# 视图表与客户端重构总计划

> 版本：v3
> 状态：待确认
> 日期：2026-11-20
> 依据：`docs/草稿纸/23-视图表与终端视图契约.md`、`docs/草稿纸/24-客户端代码整理与重构.md`
> v3 变更：按子代理的严格审查重写文件清单、构建器归属与签名、revision 语义、第 3 步拆分、旧→新映射与文档同步范围。

## 零、执行纪律

1. 任何一步出现以下情况，立即停下并在对话里 **ask**，不要自行猜测或扩大范围：
   - 快进 / 建分支 / 合并失败或冲突；
   - 编译失败且原因不在本计划范围内；
   - 需要修改计划外文件或删除计划外类；
   - 语义不确定（旧行为该保留还是替换）；
   - 构建通过但行为与预期明显不符。
2. 每步先 `gradlew build`，通过再提交；失败不提交。
3. 每步只提交一件事；提交信息 `refactor(view|network|client|ui|wand|text|docs): ...`。
4. 不推送、不加远程。
5. 本计划执行期间不改 `README.md` / `AGENTS.md`；统一放到第 8 步。

## 一、目标

1. 读侧只保留一条视图通道：`ViewTable` 全量 + `ViewTableDiff` 差量。
2. 视图表按节点聚合：不传每机器运行状态；规则速率求和、原因取最严重；保留 `INPUT_OK` 语义。
3. 客户端按 `world` / `network` / `screen` / `wand` 分层；清空 `client` 根包。
4. 两个终端拆成 Screen / Model / Layout / Render / Tooltip / Actions；共用外壳、布局、数据源、绘制件与文案。
5. 文案集中到 `screen.text`，同一轮补 `zh_cn` / `en_us`。
6. 每步构建通过并单独提交；不引入兼容层。

## 二、非目标

- 多人组队、成员角色、按工厂订阅权限。
- 关闭终端后重开走增量（仍为全量）。
- 把排序按钮完全交给 AE2（保持现有 `IconButton` + `Blitter`）。
- 改变状态机 / 协调器 / 预检的**行为**；只做移动、改名、依赖对齐。
- 新的 UI 视觉设计；只做结构拆分与已确认的绘制统一。

## 四、迁移步骤

### 第 1 步：视图表核心（不接线）

新增：

- `view/ViewHeader`：只保留界面真用到的 `hasFactory`、`storageOnline`；`revision` 放报文，不进表头。
- `view/ViewNodeCore`：节点自身字段（含四个结论字段），不含规则 / 机器。
- `view/ViewNode`：`core` + `List<ViewIoRule>` + `List<ViewMachine>`。
- `view/ViewIoRule`（内嵌 `Key`）。
- `view/ViewMachine`。
- `view/ViewTable`。
- `view/ViewNodeDiff`：`nodeId、remove、core?、ruleUpserts、ruleRemoves、machineUpserts、machineRemoves`。
- `view/ViewTableDiff`：`baseRevision、revision、header?、List<ViewNodeDiff>`。
- `factory/ViewTableBuilder`：第 1–3 步的过渡位置；最终移入 `view`，依赖单向 `view → factory/io/runtime`；第 3c 步旧构建器删除后移动。

`ViewTableBuilder` 签名（迁移阶段在 factory，3c 后移入 view）：

```
build(Factory factory, ObservationReader observations, IoForm form, LiveNodeApply liveNodes, long now)
```

数据来源：

- 规则速率：`IoAnalyzer` 的 `Stats`；
- 规则原因：`IoForm.Entry` + `PassivePlanner` 的展示原因；
- 机器活动：`IoForm` + `ObservationReader`（`inputFull`、`workState`、`sinceInputMoveTicks`）；
- 节点待投递：`LiveNodeApply` / `LiveNode`；
- 节点健康：`NodeHealthResolver` + 观测缓存。

要点：

- `ViewNode.Activity` 必须保留 **`INPUT_OK`**（ADR-040 / ADR-041 的“可输入”语义），共 8 个值；字段在 `ViewNodeCore.activity`。
- 节点四个结论字段在 Builder 内就地算；不创建 `NodeStatus`。
- 规则速率按成员求和，原因取最严重。
- 每机器活动只作 Builder 内部临时值。

验证：`gradlew build`；另加一个临时对照测试（不提交）：旧 `FactorySnapshotBuilder.machines` 与新 Builder 在同一工厂快照上的活动 / 速率 / 原因逐项一致。

### 第 2 步：网络通道与协议

新增：

- `network/ViewPort`
- `network/payload/ViewTableS2C`
- `network/payload/ViewTableDiffS2C`
- `network/payload/ViewTableRequestC2S`

报文契约：

| 报文 | 字段 |
|---|---|
| `ViewTableS2C` | `containerId、revision、pageIndex、pageCount、ViewTable page`（每页都带 header） |
| `ViewTableDiffS2C` | `containerId、baseRevision、revision、ViewTableDiff` |
| `ViewTableRequestC2S` | `containerId、knownRevision` |

分页与拼装：

- 页面单位是完整 `ViewNode`；单节点超过预算时允许单独超大页，但仍受硬上限保护。
- 客户端先收齐同一 revision 的所有页；收齐前忽略 diff；页缺失 / revision 不符 → 请求全量。

revision 语义：

- `ViewPort` 为每个工厂维护“上一次已发送的 `ViewTable`”和自增 `revision`。
- 每次 `sync` / `refresh` 都重建当前表，与基线做整表比较：
  - 相同 → 不回包；
  - 不同 → `revision++`，算 `ViewTableDiff`，发给该工厂的所有会话，更新基线。
- **不依赖 `NodeLibrary.revision`**；观测变化（掉线、恢复、开工、仓库离线）也会被重建比较捕获。

修改：

- `network/ModNetwork` → 改名 `IdleFactoryNetwork`，注册新包，`PROTOCOL_VERSION` 39 → 40；旧客户端不兼容，重进即可。
- `network/CommandPort`：删除 `containerId < 0` 早退；写命令成功后按“工厂”调 `ViewPort.refresh`，世界命令也会刷新已打开终端。
- `menu/FactoryNodeMenu`、`menu/FactoryPassiveIoMenu`：覆盖 `removed(Player)` 调 `ViewPort.close`，最后一个会话关闭时丢弃基线。

验证：`gradlew build`。

## 五、测试策略

- 第 1–7 步：每步 `gradlew build`；第 1 步额外做旧/新聚合临时对照；第 3 步与第 6 步各做一次开发自检（进世界打开两个终端），不替代用户测试。
- 全部步骤完成后，由用户按清单测试；发现问题再开修复提交。

### 用户测试清单

1. 被动 IO 终端：打开、列表 / 磁贴、搜索、排序、滚动、规则增删改、tooltip。
2. 节点终端：节点列表、展开成员、改名、阻挡 / 倍率 / 派单、定位、删除确认、tooltip。
3. 写命令：规则增删、节点删除、锚点切换；不出现“界面会话过期”。
4. 绑定杖：机器绑定 / 解绑、草稿编辑、HUD、存储杖锚点高亮、机器杖绿 / 橙 / 红。
5. 关闭终端再打开：全量刷新正常；关掉最后一个终端后，服务端不再发差量。
6. 中英文切换：tooltip、按钮、确认框、HUD 不截断、不溢出。
7. `logs/latest.log` 无异常、无协议不匹配。
8. 存档退出重进：配置与终端行为正常。

## 六、风险

| 风险 | 处理 |
|---|---|
| 每机器活动状态迁移语义偏差 | 第 1 步旧/新对照；保留 `INPUT_OK` |

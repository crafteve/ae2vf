## 〇、一句话与行为变更清单

把机器绑定杖重构成「空闲态 1:1 + 编辑态 toggle + 连锁 + 两个 AE2 外壳面板 + 统一 HUD」的工具，草稿纯客户端、提交走统一 `commit`、服务端全量校验后一次写库。

**本计划包含以下行为变更，需单独确认：**

| # | 变更 | 现状 | 计划 |
|---|---|---|---|
| B1 | 删机器不再立即退样板 | `MachineLinkService.removeMachine` 任何成功删除都 `returnPatterns`（整节点样板退光） | 仅当**节点被删除**时退样板；节点还在时保留样板 |
| B2 | 1:1 断开的判定搬到服务端 | 客户端按快照发 `MACHINE_TOGGLE` | 客户端只发 `target`，服务端现查归属决定连/断 |
| B3 | 连锁只在堆叠编辑态 | 空闲态 Ctrl+右键直接连锁建节点 | 空闲态 Ctrl+右键无操作 |
| B4 | 快照从轮询改为变更推送 | 手持杖每 2 秒请求一次 | `FactoryRuntime.markDirty` 统一推 |

## 一、范围与非目标

### 1.1 范围

- 机器绑定杖：手势、两个面板、HUD、世界框、网络包、服务端校验与写库、连锁。
- 与节点终端衔接：终端 `+` 进入编辑态。
- 协议 29 → 30。
- `WandLinkRenderer` **接管两把绑定杖的世界框**（机器杖绿/黄/红，存储杖蓝），删除旧 `FactoryLinkRenderer` 时不能丢存储杖功能。

### 1.2 非目标

- 不改节点 / 机器 / 方块三层模型与健康语义（沿用编号 15）。
- 不做 `STACKED_MULTIBLOCK` 交互；线上枚举直接拒绝（见 §7.2）。
- 不改存储绑定杖的绑定逻辑（只接管它的世界框渲染）。
- 不做曲线、悬停高亮、世界内提交动画。
- 不做服务端草稿会话。

### 2.2 依赖方向

```
item ──(Dist 安全桥)──► client.wand.WandGesture
client.wand.* ──► network.payload.wand.*, factory.wand.*（只读 record）
client.wand.screen.* ──► client.wand.*, menu.wand.*

network.payload.wand.* ──► factory.WandService / factory.WandValidator（同包可见）
factory.WandService ──► factory.wand.*（只读 record）、factory 现有写入口
```

- `factory.WandService` **返回领域结果 `WandCommitOutcome`，不 import 任何 `network.payload`**，由包 handler 组装 `S2C`。
- `factory.wand` 不放服务实现，只放纯数据；服务实现放 `factory` 顶层，因为 `NodeLibraryService` / `MachineLinkService` 是包私有，跨包不可见。
- `item` 不直接 import `client.wand.*`。

### 2.3 状态归属表（补全）

| 状态 | 权威 | 写入者 | 读者 | 生命周期 |
|---|---|---|---|---|
| 草稿（mode/nodeId/added/removed/open/requestSeq） | 客户端内存 | `WandSession` | 手势、HUD、两个 Screen、提交 | 编辑态创建；成功/取消/换手/换维度/登出销毁 |
| 节点库 | 服务端存档 | `WandService` → `NodeLibraryService` | 运行时、终端、快照 | 永久 |
| 链接快照 | 服务端，客户端只读缓存 | `FactoryLinksS2C` | 渲染、`WandPrecheck`、GUI-2 | 登录/打开终端/`markDirty` 时推；登出清 |
| **服务端每玩家 requestSeq** | 服务端内存 | `WandService.commit`（仅成功时推进） | 幂等判断 | 玩家下线清（`PlayerLoggedOutEvent`） |
| **服务端每玩家提交节流（200ms）** | 服务端内存 | `WandService.commit` | 幂等/防连点 | 同上 |
| **预校验 issues** | 客户端内存 | `WandOpenS2C` 处理 | `WandDraftScreen` | 收到时缓存；Screen 关闭清 |
| **提交回执** | 客户端内存 | `WandCoordinator` | GUI-2 / HUD | 处理完或超时后清 |
| **HUD 状态** | 客户端内存 | 事件 + tick | `WandHud.render` | 编辑态常驻；闪条到期清 |
| 客户端「方块→节点」索引 | 客户端内存 | **只有 `WandLinks`** | 手势、`WandPrecheck` | 随快照整体替换 |

> 旧的第二条索引 `ClientFactoryTableHandler.rememberNode` → `BindingDraftController.blockToNode` 必须删除，统一到 `WandLinks`（见 §12）。

### 2.4 线程边界

| 代码 | 线程 | 约束 |
|---|---|---|
| `network.payload.wand.*.handle` | Netty → `context.enqueueWork` → 服务端主线程 | 解码只读缓冲 |
| `WandService` / `WandValidator` | 服务端主线程 | 无锁；节点库只在此线程写 |
| `WandChain` BFS | 服务端主线程 | 受 `FactoryLinkFinder` 上限 |
| `WandSession` / `WandPrecheck` | 客户端主线程 | 不碰服务端状态 |
| `WandLinkRenderer` / `WandHud` | 客户端渲染线程 | 只读快照 / `HudState` |

### 2.5 一条完整提交链

```
点击确定 → WandDraftScreen → WandCoordinator.submit()
→ WandCommitC2S(containerId, intent, target, mode, nodeId, requestSeq, added, removed)
→ 服务端 enqueueWork
→ WandService.commit
   → WandValidator.validate（只读，含 LinkGate + machineAt 两条占用检查）
   → 计算 finalMachines
   → finalMachines == 0：batch.remove(nodeId) + 退样板
   → finalMachines > 0：batch.replace(candidate)，检查 REPLACED
   → batch.close()（触发 markDirty：存档 + 索引重建 + 快照推送）
   → 副作用：observations.refresh(新增块)、nodeIoRunner.forget(removed)、nodeManager.refreshPatterns
→ 包 handler 组装 WandCommitS2C 回发
→ 客户端 WandCoordinator：匹配 requestSeq → 清草稿 / 标红
```

## 三、领域模型

### 3.1 枚举（收敛后）

```java
public enum WandMode { SINGLE, STACK, MULTIBLOCK }   // STACKED 不进线上

public enum WandIntent { BIND, UNBIND }

public enum WandPanel { MODE, DRAFT }

public enum WandFailure {
    NONE,
    EMPTY_DRAFT,
    NOT_HOLDING_WAND,
    NO_FACTORY,
    STALE_REQUEST,
    INVALID_REQUEST,
    NODE_NOT_FOUND,
    MODE_MISMATCH,
    TYPE_MISMATCH,          // 机器类型与节点不一致（合并原两个）
    DUPLICATE_BLOCK,
    BLOCK_CLAIMED,          // 任何节点已占用（本节点或别节点）
    BLOCK_UNLOADED,
    NOT_A_MACHINE,
    LIMIT_NODES,
    LIMIT_MACHINES,
    LIMIT_BLOCKS,
    DELETE_BLOCKED,         // 删除被拒（规则/样板/最后一台），detail 说明原因
    MEMBER_NOT_REMOVABLE    // 堆叠/多方块成员不能从 1:1 断开
}
```

- `STACKED_MULTIBLOCK` 从线上枚举删除；数据模型段落如需保留历史，放注释，不进 codec。
- `DELETE_BLOCKED` 覆盖原 `NODE_BUSY` 与 `LAST_MACHINE_WITH_RULES`；detail 交给客户端文案函数按 `WandIssue.reason` 细分（`reason` 用独立枚举 `WandBlockReason`，不放网络主枚举里）。
- 解码跟随现有风格：`readUnsignedByte` + 范围检查 + `DecoderException`（对齐 `FactoryBindingCommitC2S`）。

### 3.2 `WandDraft`

```java
public record WandDraft(
    WandMode mode,
    @Nullable UUID nodeId,
    List<WandMachineDraft> added,
    Set<UUID> removed,
    @Nullable WandMachineDraft open,
    long requestSeq
)
```

不变量：

1. `added` 每台 blocks 非空，`blocks.get(0)` 是主方块。
2. `added` + `open` 的方块全局不重复。
3. `removed` 非空时 `nodeId` 非空。
4. `mode` 与结构一致：`SINGLE` = 1 台 1 块；`STACK` = 每台 1 块；`MULTIBLOCK` = 恰好 1 台。
5. `open` 仅 `MULTIBLOCK` 使用。
6. `requestSeq` 由 `WandSession` 分配，跨草稿单调（见 §6.4）。

### 3.3 `WandCommitOutcome`（领域结果，不依赖网络包）

```java
    WandFailure failure,
    @Nullable UUID nodeId,

```

## 四、交互

### 4.1 状态机

`WandSession.State`：`IDLE` / `EDITING` / `SUBMITTING`。

- `SUBMITTING` 期间：toggle、连锁、打开 GUI 全部忽略（HUD 显示「提交中…」）。
- 超时 / 失败 → 回 `EDITING`。
- 成功 → `IDLE`。

### 4.2 手势

见草稿 16 §1。要点：

- 左键不注册监听；`MachineBindingWandItem.onItemUseFirst` 只拦右键。
- 空闲态蹲下右键（方块或空气）→ `WandOpenC2S(MODE)`。
- 编辑态蹲下右键 → `WandOpenC2S(DRAFT, draft)`。
- 编辑态（堆叠）Ctrl+右键 → `WandChainC2S(origin)`。

### 4.3 两个 GUI

- GUI-1：堆叠 / 多方块。
- GUI-2：草稿行 + 取消/确定；预校验失败行标红、确定灰显。
- 无背包槽（见 §10.2）。

### 4.4 连锁

- 仅堆叠编辑态。
- 上限在 BFS 内结算（128 台 / 4096 访问 / 半径 32），**LinkGate 过滤在前述上限之后**，过滤后数量可少于 128（与现有 `FactoryLinkFinder` + `LinkGate` 行为一致）。
- 客户端过滤：草稿重复、类型不一致、编辑已有节点时属于本节点。
- HUD：`已连锁加入 N 台（跳过 M 台）`。

### 4.5 HUD

- 统一 `WandHud`，事件改 `HudState`，`RenderGuiLayerEvent` 每帧读。
- 编辑态常驻；闪条 60 tick。
- 文案集中 `WandMessages`。

## 六、网络层

### 6.1 包清单

| C2S | S2C | 说明 |
|---|---|---|
| `WandOpenC2S` | `WandOpenS2C` | 开面板；DRAFT 带草稿做预校验 |
| `WandChainC2S` | `WandChainS2C` | 连锁 |
| `WandCommitC2S` | `WandCommitS2C` | 提交 |
| `FactoryLinksRequestC2S` | `FactoryLinksS2C` | 快照请求 / 推送 |

原版 `OpenScreen` 由 `openMenu` 自动发。

### 6.2 codec

- 跟随现有 `FactoryBindingCommitC2S` 的写法：手写 `StreamCodec.of`、`readUnsignedByte` + 范围检查 + `DecoderException`；不用 `readEnum`。
- `WandDraft` 的 codec 独立在 `network/payload/wand/WandDraftCodec`（静态工具），编码顺序与 `WandDraft` 字段顺序严格一致。
- 解码上限：机器数、单机器块数、总块数、removed 数、issues 数各 `min(config, HARD_WIRE_ENTRIES)`；累计总块数校验。

### 6.3 快照结构

```java
record FactoryLinksS2C(List<NodeLink> nodes, List<Link> storage, long revision)
record NodeLink(UUID nodeId, ResourceLocation typeBlockId, List<MachineLink> machines)
record MachineLink(UUID machineId, List<Link> blocks, BlockKey primary)
record Link(ResourceKey<Level> dimension, BlockPos pos)
```

- 三层各自解码上限 + 总量上限。
- 客户端建 `BlockKey → (nodeId, machineId)` 索引。

### 6.4 幂等（requestSeq）

- 客户端 `WandCoordinator` 持有**每玩家单调计数器**：`nextSeq()` 返回 `++counter`。
- 草稿每次变更取一次新 seq；提交带当前 seq。
- 服务端 per-player `lastAcceptedSeq`：**只有 commit 成功才推进**；失败不推进。
- `commit` 收到 `requestSeq <= lastAcceptedSeq` → `STALE_REQUEST`。
- `WandCommitS2C` 回带 `requestSeq`；客户端只在等于当前 seq 时处理，迟到回执丢弃。
- 服务端记录在 `PlayerLoggedOutEvent` 清理；登出/死亡/换维不清（避免重登后旧序号被拒）。

### 6.5 推送

- `FactoryLinksS2C` 挂在 `FactoryRuntime.markDirty()`（`save + links.rebuild + requestReconcile` 的唯一出口）：对该工厂的在线归属者推送。
- 登录、打开终端、`FactoryLinksRequestC2S` 也触发全量。
- 不再 2 秒轮询。

### 6.6 时序

```
开 GUI-1：C2S(MODE) → 校验 → openMenu
开 GUI-2：C2S(DRAFT, draft) → validate（只读）→ 先发 WandOpenS2C(issues) → 再 openMenu
          （客户端缓存 issues；Screen 打开时读取）
确定：C2S(commit) → validate → commit → S2C + 快照
连锁：C2S(origin) → BFS → S2C(machines)
```

先发 issues 再 openMenu，避免屏幕先开、问题后到导致的闪烁。

### 6.7 协议

`PROTOCOL_VERSION` 29 → `"30"`。开发期不保 29 兼容。

## 七、服务端

### 7.1 入口（放 `factory` 顶层，非 `factory.wand`）

```java
final class WandService {   // package-private，同包访问 NodeLibraryService
    WandOpenResult validate(ServerPlayer player, WandIntent intent, WandMode mode,
            @Nullable UUID nodeId, List<WandMachineDraft> added, List<UUID> removed);
    WandCommitOutcome commit(ServerPlayer player, WandCommitRequest request);
    List<BlockKey> chain(ServerPlayer player, BlockKey origin);
}
```

- `WandCommitRequest` 是 `factory` 内部的纯数据（从网络 record 拷来），避免 `factory` 依赖 `network`。
- 包 handler 负责：网络 record ↔ 内部数据、`WandCommitOutcome` → `WandCommitS2C`。

### 7.2 `validate`（只读，顺序固定）

1. 主手是绑定杖（世界提交）。
2. 工厂存在且归属玩家。
3. `mode` 必须是 `STACK` / `MULTIBLOCK`（1:1 用 `SINGLE`）；`STACKED` → `MODE_MISMATCH`。
4. 草稿非空；`mode` 与 `added` 分组自洽。
5. 每台机器非空；单机器块数 ≤ `maxBlocksPerMachine`。
6. `added` 全局无重复块。
7. `removed` 每个 machineId 属于 `nodeId`。
8. 占用检查**两条都要**：
   - `factory.config().nodes().machineAt(block)` 存在 → `BLOCK_CLAIMED`（防本节点内重复块）；
   - `LinkGate.check(...)` 别的工厂占用 → `BLOCK_CLAIMED`。
9. 每个 `added` 块：区块加载、方块实体存在、是有效机器（`FactoryLinkFinder.isMachine`）。
10. 类型一致：`added` 每台主方块 id 相同；编辑时与 `node.typeBlockId` 一致 → `TYPE_MISMATCH`。
11. 上限：节点数（新建）、每节点机器数、每节点方块数、全工厂总量。
12. 计算 `finalMachines = base.machineCount() - removed.size() + added.size()`：
    - `finalMachines == 0` 且节点有规则 / 样板 → `DELETE_BLOCKED`；
    - 1:1 断开且节点有规则 / 样板 → `DELETE_BLOCKED`；
    - 1:1 断开目标是多机节点成员 → `MEMBER_NOT_REMOVABLE`。
13. `intent == UNBIND` 时 `target` 必填，且能定位到机器。

输出 `List<WandIssue>`（空 = 通过）。

### 7.3 `commit`（原子写）

`NodeLibraryService.Batch` **不是事务**，所以：

1. 先 `validate` 全量；失败直接返回，不改状态。
2. 计算 `finalMachines`：
   - `finalMachines == 0` → `batch.remove(nodeId)`，检查返回 `true`；退样板；`nodeManager.removeNode`；`nodeIoRunner.forget` 每个 removed。
   - `finalMachines > 0` → `candidate = base.withAddedMachine(...).withRemovedMachine(...)`（**注意 `withRemovedMachine` 在只剩 1 台时返回 `this`，所以 0 台必须走 remove 分支**）；`batch.replace(candidate)`，返回值必须是 `REPLACED`，否则整份失败。
3. `batch.close()` → `markDirty`（存档标记 + 索引重建 + 快照推送）。
4. 副作用（在 `close` 之后、同一主线程序列内）：
   - 新增 / 变更块：`observations.refresh(block)`（**不能漏**，否则刚绑上显示离线）。
   - removed machineId：`nodeIoRunner.forget(id)`。
   - `nodeManager.refreshPatterns(nodeId)`。
5. 失败路径：validate 之后 `batch` 不应失败；若 `replace` 意外返回非 `REPLACED`，返回 `INVALID_REQUEST` 并记录日志（不改状态，因为 `close` 未到）。

**副作用抽离**：`MachineLinkService` 增加 `applyRemovalSideEffects(factory, oldNode, removedMachines)`，`removeMachine` 与 `WandService` 共用，保证「删机器」只有一套副作用。

### 7.4 失败映射

`WandFailure` 见 §3.1。`rejected` 列表最多 32 个；`rejectedCount` 给全量数量（GUI-2 的「先修正 N 处」用）。

### 7.5 删到 0 台与样板（B1）

- 仅当**节点被删除**才 `returnPatterns`。
- 现有 `removeMachine` 在任何删除前都退样板，改为只在 `nodeDeleted` 时退。
- 节点有规则 / 样板时删最后一台 → `DELETE_BLOCKED`（用户已确认）。

### 7.6 连锁

`chain(player, origin)`：

1. 校验主手 / 工厂 / 维度。
2. `FactoryLinkFinder.machines(level, pos)`（内部已含 128 / 4096 / 32 上限）。
3. `LinkGate.of(manager)` 过滤别的工厂占用。
4. 返回列表，不写库。

### 7.7 线程与状态

- 全部主线程。
- `lastAcceptedSeq` / 节流时间戳：`Map<UUID, PlayerWandState>`，玩家下线清。
- `validate` 与 `commit` 之间隔一个 tick，`commit` 必须重新 validate。

## 八、客户端

### 8.1 `WandSession`

- 状态：`IDLE` / `EDITING` / `SUBMITTING`。
- `startNew(WandMode)`、`startEdit(UUID nodeId, WandMode mode)`、`toggle(BlockKey)`、`addAll(List<BlockKey>)`、`removeMachine(UUID)`、`clear()`、`snapshot()`。
- `startEdit` 的 mode：从 `WandLinks` 读该节点的机器结构；单块机器 → `STACK`，多块 → `MULTIBLOCK`；快照缺失回退 `STACK`。
- `startEdit` 保留「主手是绑定杖」前置（否则下一 tick 会被换手规则清掉）。

### 8.2 `WandPrecheck`

- 纯函数：`List<WandIssue> check(WandDraft, ClientLevel, WandLinks)`。
- 只做客户端能做的：方块实体、类型一致、已属于别的节点、重复。
- 只用于即时红框与 HUD；GUI-2 以服务端 issues 为准。

### 8.3 `WandCoordinator`

- `nextSeq()` 单调计数器（跨草稿）。
- 提交锁 1s、超时 5s。
- 回执按 `requestSeq` 匹配；不匹配丢弃。
- 超时：回 `EDITING`，HUD 「服务端未响应」，允许用新 seq 重试。

### 8.4 `WandLinks`

- 快照缓存 + `BlockKey → (nodeId, machineId)` 索引。
- 整体替换，不累积。
- 删除 `ClientFactoryTableHandler.rememberNode` 与 `BindingDraftController.blockToNode`；唯一入口 `WandLinks.update(FactoryLinksS2C)`。

### 8.5 生命周期

- 登录：清草稿 / HUD / 回执；保留 `WandLinks` 直到快照到达；请求一次快照。
- 登出：全清（含 `nextSeq` 计数器）。
- 换维度：清草稿。
- 换手 / 打开别的界面 / 死亡：清草稿。
- **例外**：`minecraft.screen instanceof WandModeScreen || WandDraftScreen` 时不触发「打开别的界面清草稿」。

### 8.6 GUI-2 的 issues 缓存

- 收到 `WandOpenS2C` 时按 `panel` 缓存到 `WandCoordinator.pendingIssues`。
- `WandDraftScreen` 构造时读取；关闭时清。
- `openMenu` 与 `WandOpenS2C` 的先后不保证，所以按「到达即缓存」而不是「Screen 构造时请求」。

## 十、GUI（AE2 外壳）

### 10.1 结论前置

AE2 19.2.10 的 `AEBaseMenu` 第 4 个参数只接受 `BlockEntity` / `IPart` / `ItemMenuHost`，**没有 `MenuHost` 接口**。所以计划走 AE2 正规路径：

- `MachineBindingWandItem implements IMenuItem`，实现 `getMenuHost(player, locator, hit)` 返回 `WandMenuHost`。
- `WandMenuHost extends ItemMenuHost<MachineBindingWandItem>`。
- `ModMenus` 用 `MenuTypeBuilder.<WandMenu, WandMenuHost>create(...).buildUnregistered(...)`。
- 打开：服务端用物品定位器（主手）打开，不用 `SimpleMenuProvider`。
- 阶段 3 第一件事是验证这个打开路径；若 locator 拿不到，退回纯客户端 Screen（需同步删 `WandOpenC2S/S2C`、`WandMenu`，并重新定义 commit 的 `containerId` 校验）。

### 10.2 无槽位

两个面板是对话框，不显示玩家背包：`WandMenu` 不调 `createPlayerInventorySlots`；style 用 AE2 的 dialog 文档（`/screens/priority.json` 或 `/screens/craft_confirm.json`），不要 `base_terminal.json`（后者带终端布局）。

### 10.3 style 文档

`StyleManager.loadStyleDoc` 硬编码 `ae2` 命名空间，**项目自己的 `assets/idlefactory/screens/*.json` 加载不到**。因此：

- 直接用 AE2 自带 dialog style：`/screens/priority.json`（176×125，标题 + 两个按钮位）或 `/screens/craft_confirm.json`（238×206，带滚动条和确定/取消）。
- 面板内容自绘；按钮用 AE2 的 `AEButton` 或 style 声明。
- 不新增 `assets/idlefactory/screens/*.json`。

### 10.4 菜单归属校验

- 不改 `FactoryGuiOpening.isFactoryMenu`（它服务机器表 / 规则 / 仓库 / 节点动作）。
- 新增 `FactoryGuiOpening.isWandMenu(menu, containerId, panel)`：`containerId` 匹配 + `menu instanceof WandMenu` + `menu.panel() == panel`。
- `commit` 的 GUI 提交要求 `panel == DRAFT`。

### 10.5 数字键

GUI-1 的 `1/2` 直选会与 `AbstractContainerScreen.checkHotbarKeyPressed` 冲突；`WandModeScreen` 重写 `checkHotbarKeyPressed` 拦截数字键，避免切快捷栏导致换手清草稿。

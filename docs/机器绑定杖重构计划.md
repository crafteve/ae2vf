## 〇、为什么整份重写

v2 写在 ui-v3、多方块仍在、协议 29 的假设上。同一个 11 月 10 日，ADR-039 把分支收窄为单方块模型，v2 的这些前提已经消失：

| v2 的前提 | 现状 |
|---|---|
| 一台机器占 1..M 个方块，草稿里每台机器带方块列表与主方块 | Machine(UUID id, BlockKey block)，机器 = 一个方块；Node 只持 List<Machine> |
| WandMode 有 SINGLE / STACK / MULTIBLOCK，线上还要拒绝 STACKED | BindingMode 只剩 SINGLE / STACK（factory/BindingMode.java:14,:16），全仓 0 个 MULTIBLOCK 标识符，仅 :9 一处历史注释 |
| 协议 29 → 30 是本次任务 | PROTOCOL_VERSION 已是 "30"（network/ModNetwork.java:34），本计划改为 30 → 31 |
| 要兼容 / 清理第一版工作台与 /idf 指令 | 已整体删除（ADR-039），只剩注释残留 |
| 每节点方块数、单机器块数上限 | FactoryLimitsConfig 只有节点数 / 单节点机器数 / 全工厂机器数（:44-54）以及规则数 / 名字长度 / 观测调优；方块维度上限随多方块一起消失 |

所以这不是把 v2 里的 MULTIBLOCK 字样删掉：模式概念、GUI-1、每机器方块列表一消失，**草稿模型、面板数量、网络包、校验分支、渲染数据源**都跟着变。

本次两项已确认的收敛（2026-11-10）：

1. **删除 GUI-1 与「模式」**：只剩空闲态（1:1）与编辑态（草稿），蹲下右键直接进编辑态。
2. **没有工厂时只用 HUD 提示，不自动建厂**：建厂仍只发生在两个终端打开时。

结果：绑定杖 = 空闲态 1:1 toggle + 编辑态草稿（可加可删）+ 连锁 + 一个确认面板 + 一条 HUD + 三色世界框。草稿没有 mode、没有每机器方块列表、没有「主方块」。

## 一、范围与非目标

### 1.1 范围

- 机器绑定杖：手势、草稿状态机、连锁、确认面板、HUD、世界框、网络包、服务端校验与写库。
- 与节点终端衔接：终端 + 进编辑态。
- 链接快照：从「扁平坐标 + 2 秒轮询」改成「节点 / 机器 / 方块三层 + 变更推送」。
- 协议 30 → 31；删除草稿物品组件。
- 顺手修正本次触碰文件里指向已删功能（指令 / 工作台 / 多方块）的注释。

### 1.2 非目标

- 不做多方块：不预留枚举、不预留字段、不写「以后扩展」分支。
- 不做模式切换、GUI-1、滚轮切模式。
- 不恢复聊天指令入口，不恢复第一版工作台。
- 不改节点 / 机器 / 规则 / provider / 健康模型，不改 IO。
- 不改存储绑定杖的绑定逻辑；只把它的世界框渲染并进新渲染器。
- 不做曲线、准星悬停、世界内提交动画、绑定距离校验。
- 不做服务端草稿会话；草稿仍是客户端内存，提交时一次上传。
- 不自动建厂（见 §4.6）。

### 3.2 三个结构性问题

1. **快照不够用**：FactoryLinksS2C(mode, storage, machines) 只有坐标（:40），客户端不知道方块属于哪个节点、哪台机器。「世界蹲下右键编辑已有节点」靠机器表处理器 rememberNode（ClientFactoryTableHandler:30），而机器表只由被动 IO 终端请求（FactoryPassiveIoScreen:547）——本会话没开过那个终端就没有映射。新快照必须带 nodeId / machineId / typeBlockId。
2. **判定写了两遍**：客户端 BindingDraftController 有一套「SINGLE 就 toggle、STACK 就加」的手势判断（:102-142），服务端 BindingService.toggleMachines 又有一套「全连才断、否则补齐」的判断（:227-255）；1:1 的语义两边各写一半。
3. **失败语义是字符串**：BindingResult.message、FactoryBindingCommitS2C.message、聊天栏文案。客户端无法按原因分支（标红哪一行、HUD 说什么），也无法穷尽检查。

### 3.3 v2 中已失效、不应再出现的引用

- WandMode 与 MULTIBLOCK / STACKED_MULTIBLOCK；WandDraft.open、每机器 blocks 列表。
- MAX_DRAFT_BLOCKS、maxBlocksPerMachine、每节点方块数上限。
- 协议 29 → 30；§14.3 的多方块测试场景（Ctrl 右键、一台 4 块、右键主方块整台移除）。
- 测试场景里的「命令删节点」——指令已删除，只剩终端删除。
- 「markDirty 已推包」的判断——现在不推，是要新建的能力。
- 「MachineBindingWandItem 已是 IMenuItem」——它仍是 extends Item（:18）。

## 四、交互

### 4.1 状态

唯一状态机：IDLE / EDITING / SUBMITTING，**没有 mode 字段**。

- IDLE：手持机器杖、草稿为空。普通右键 = 1:1 toggle；蹲下右键 = 进 EDITING 新建草稿。
- EDITING：草稿开放。nodeId == null 是新建，非空是编辑已有节点；HUD 常驻。
- SUBMITTING：等提交回执，所有手势忽略；成功回 IDLE，失败 / 超时回 EDITING。

~~~mermaid
stateDiagram-v2
    [*] --> IDLE
    IDLE --> EDITING: 蹲下右键（方块或空气）
    EDITING --> SUBMITTING: 面板点确定
    SUBMITTING --> IDLE: 成功
    SUBMITTING --> EDITING: 失败 / 超时
    EDITING --> IDLE: 取消 / 换手 / 换维度 / 登出 / 打开别的界面
    IDLE --> IDLE: 右键方块（1:1 toggle）
~~~

### 4.2 手势表

| 状态 | 输入 | 行为 |
|---|---|---|
| IDLE | 右键方块 | 发 WandToggleC2S，服务端连或断 |
| IDLE | 蹲下右键（方块或空气） | 进入 EDITING，新建草稿，不弹任何界面 |
| IDLE | 左键 | 不拦、不监听（正常挖方块） |
| IDLE | 蹲下滚轮 | 无操作 |
| EDITING | 右键方块 | 草稿 toggle（按 §4.3） |
| EDITING | Ctrl + 右键方块 | 连锁加入附近同 id 机器（§4.4） |
| EDITING | 蹲下右键（方块或空气） | 服务端预校验 → 打开草稿确认面板（§5） |
| EDITING | 左键 | 不拦、不监听 |
| EDITING | 蹲下滚轮 | 无操作 |
| SUBMITTING | 全部 | 忽略，HUD 显示「提交中…」 |

关键点：

- **方块与空气完全等价**：PlayerInteractEvent.RightClickBlock 与 RightClickItem 走同一个 WandGesture 入口；方块不参与判断，也不自动加入草稿。
- **编辑已有节点只走终端 +**（FactoryNodeActions.edit:90）；世界里右键自己的成员只是普通 toggle 被服务端拒绝。
- **左键完全不拦**：删除 FactoryWandEvents 里的机器杖分支，只留存储杖。
- **没有「选类型」步骤**：新建草稿永远是堆叠语义，单台走 1:1。

### 4.3 草稿 toggle 规则

客户端用 WandLinks 的 BlockKey → 归属索引分三态；服务端提交时全量重验：

| 方块状态 | 新建草稿（nodeId = null） | 编辑已有节点 |
|---|---|---|
| 未绑定 | 加入 added | 加入 added |
| 已在 added | 从 added 移除 | 从 added 移除 |
| 属于本节点 | 拒绝 BLOCK_CLAIMED（新建草稿没有本节点，任何已归属方块都算被占用） | 标记删除进 removed；再右键撤销 |
| 属于别的节点 | 拒绝 BLOCK_CLAIMED | 拒绝 BLOCK_CLAIMED |
| 无方块实体 | 拒绝 NOT_A_MACHINE | 同 |
| 区块未加载 | 拒绝 BLOCK_UNLOADED | 同 |
| 类型不一致 | 拒绝 TYPE_MISMATCH | 拒绝 TYPE_MISMATCH |

- 类型基准：新建草稿 = 第一台加入的方块 id（客户端读 level.getBlockState）；编辑已有节点 = 快照里的 node.typeBlockId。
- 草稿被 toggle 到 0 台：保持 EDITING，HUD 显示 0 台；不自动退出。
- 草稿里的方块被挖掉：下次右键 / 开面板 / 提交前检测到，标红提示，可手动移除。
- 客户端拒绝 = 即时红字 + 音效，不加入草稿。

### 4.4 连锁（Ctrl + 右键，仅 EDITING）

~~~text
客户端 EDITING，Ctrl + 右键方块
→ WandChainC2S(origin)
→ 服务端：主手 / 工厂校验 → FactoryLinkFinder.machines(level, pos)（128 台 / 4096 访问 / 半径 32）
         → LinkGate.of(manager).filter(...) 过滤别家占用
→ WandChainS2C(machines, failure)
→ 客户端按「已在草稿 / 类型不一致 / 属于本节点 / 属于别的节点」跳过
→ 批量加入 added → HUD 闪 3 秒「已连锁加入 8 台（跳过 3 台）」
   （跳过数只统计客户端跳过：已在草稿 / 类型不符；被别家占用的由服务端静默过滤，不回数字段）
~~~

- 连锁只往草稿里加，不直接建节点。
- 上限在 BFS 内结算（过滤前），过滤后不补位、不重扫，与现有 FactoryLinkFinder 一致。
- 全部被跳过时 HUD 给具体原因（都在草稿里 / 类型不一致 / 附近没有同 id 机器）；「被别家占用」的数量不回传，别在文案里承诺这个数。

### 4.5 生命周期（草稿何时丢）

- 登录：清草稿 / HUD / 回执；请求一次快照。
- 登出：全清，含 nextSeq 与 WandLinks。
- 换维度 / 换手 / 把杖放进容器 / 死亡 / 打开别的界面：丢草稿回 IDLE。
- 例外：当前 screen 是 WandDraftScreen 时不丢。
- 关闭面板（Esc / 关闭按钮）回 EDITING，草稿保留；取消才丢。
- 提交中换手：回 IDLE；迟到回执按 requestSeq 丢弃。

### 4.6 没有工厂时

- 建厂只发生在两个终端打开时：FactoryPassiveIoHost:36 / FactoryNodeHost:31 调 FactoryService.ensureFactory。
- 绑定杖不建厂：服务端回 NO_FACTORY，HUD 红字「先打开一次终端（被动 IO 或节点管理）会自动建厂」，3 秒。
- 这条替换掉现在 BindingService.owned 的聊天栏文案（:397）。

## 五、草稿确认面板（唯一 GUI）

### 5.1 内容

~~~text
┌──────────────────────────────┐
│  绑定杖 · 草稿                │
├──────────────────────────────┤
│  新建 · 3 台                  │
│  ▣ 熔炉   (-12, 64, 8)        │
│  ▣ 熔炉   (-12, 64, 9)        │
│  ✕ 熔炉   (-12, 64, 10)  删除 │
├──────────────────────────────┤
│  先修正 2 处                  │
│              [ 取消 ] [ 确定 ]│
└──────────────────────────────┘
~~~

- 每行：图标 + 方块名 + 坐标；删除态红字 + 删除标记。
- 行纯展示，不响应点击；撤销删除回世界右键。
- 行数超过可视区时滚动。草稿为空时服务端按 EMPTY_DRAFT 拒绝开面板（客户端也先拦一次），面板里的空态只是兜底绘制。
- 顶部一行摘要：新建 / 编辑节点名 · 加 N / 删 M。
- 预校验有 issue：对应行标红、面板底部列原因、确定灰显。

### 5.2 状态与按键

| 操作 | 行为 |
|---|---|
| 确定 | 先 renewRequestSeq() 再入 SUBMITTING，按钮灰显，状态行显示「提交中…」；成功关面板 + 清草稿 + HUD 绿字；失败留面板标红可重试 |
| 取消 | 丢草稿，关面板，回 IDLE |
| Esc / 关闭按钮 | 回 EDITING，草稿保留 |
| 5 秒无回执 | 留面板，提示「服务端未响应」，确定恢复可点（用新 requestSeq 重试） |

### 5.3 菜单与打开路径

- WandMenu extends AEBaseMenu，**无玩家槽位**（不调 createPlayerInventorySlots）。
- MachineBindingWandItem implements IMenuItem；WandMenuHost extends ItemMenuHost；ModMenus 注册 wand_draft。
- 打开由服务端做：WandOpenC2S → 只读预校验 → 先回 WandOpenS2C(issues) → 再 openMenu（物品定位器，不用 SimpleMenuProvider）。有 issue 也开（行标红、确定灰显）；`WandOpenResult.failure != NONE`（未持杖 / 无工厂等）不开面板，只回 HUD。
- style 用 AE2 自带 dialog：/screens/craft_confirm.json（238×206，带滚动条与确定/取消）。StyleManager.loadStyleDoc 固定 ae2 命名空间，不新增项目自己的 screen json；草稿行自绘。
- FactoryGuiOpening 加 isWandMenu(menu, containerId)；isFactoryMenu 不动（它只服务两个终端）。
- **回退方案（阶段 3 首验）**：若 IMenuItem / 定位器打不开菜单，退纯客户端 Screen：删 WandOpenC2S/S2C、WandMenu、WandMenuHost 及 ModNetwork 的对应注册，预校验改成独立的请求 / 回包，commit 的 containerId 固定 0；协议仍是 31（开发期未发布，不必再递增）。发现打不开就停下来改方案，不硬撑。

## 六、HUD

### 6.1 四种形态

| 形态 | 触发 | 文案示例 | 时长 | 颜色 |

### 6.2 规则

- 单行，底部居中，AE2 深底浅字；左状态点 / 中文案 / 右按键提示。
- 常驻条左区：新建 / 编辑 + 台数；右区：当前可用动作（右键加机器 / 蹲下右键确认），随状态变化。

## 七、数据与契约

### 7.1 草稿

~~~java
public record WandDraft(
    @Nullable UUID nodeId,      // null = 新建节点
    List<BlockKey> added,       // 待加入的机器，每台一个方块
    Set<UUID> removed,          // 待删除的已有机器 id；仅编辑已有节点时非空
    long requestSeq             // 版本号，防重放
)
~~~

不变量：

1. added 内方块不重复。
2. nodeId == null 时 removed 必须为空。
3. removed 每个 id 必须属于 nodeId 的节点（客户端靠快照保证，服务端重验）。
4. 草稿规模 added.size() + removed.size() 不超过 min(maxMachinesPerNode, HARD_WIRE_ENTRIES)：这是解码防爆量上限；玩法上限由 finalMachines 在服务端判（§9.2 第 10 条）。
5. 编辑已有节点时，added 的方块不能与该节点现有机器重复；服务端以 machineAt 为准。
6. added 的方块与 removed 机器对应的方块不相交（客户端 toggle 天然保证，服务端仍要查）。

### 7.2 枚举

~~~java
public enum WandFailure {
    NONE, EMPTY_DRAFT, NOT_HOLDING_WAND, NO_FACTORY, STALE_REQUEST, INVALID_REQUEST,
    NODE_NOT_FOUND, TYPE_MISMATCH, DUPLICATE_BLOCK, BLOCK_CLAIMED, BLOCK_UNLOADED,
    NOT_A_MACHINE, LIMIT_NODES, LIMIT_MACHINES, DELETE_BLOCKED, MEMBER_NOT_REMOVABLE
}

public enum WandDeleteReason { NONE, HAS_RULES, HAS_PATTERNS }
~~~

- DELETE_BLOCKED 带 WandDeleteReason，客户端据此出文案。
- MEMBER_NOT_REMOVABLE：1:1 断开的是一台多机节点的成员。
- 没有 LIMIT_BLOCKS、MODE_MISMATCH、STACKED_MULTIBLOCK。

### 7.3 结果

~~~java
public record WandCommitOutcome(
    boolean ok, WandFailure failure, WandDeleteReason reason,
    @Nullable UUID nodeId, int addedMachines, int removedMachines,
    List<BlockKey> rejected, int rejectedCount)
~~~

1:1 toggle 用同一份结果结构（nodeId 为落到的节点）。

### 7.4 上限

| 项 | 值 | 位置 |
|---|---|---|
| 连锁台数 / 访问 / 半径 | 128 / 4096 / 32 | FactoryLinkFinder（复用） |
| 线协议条目硬上限 | 32768 | ModNetwork.HARD_WIRE_ENTRIES |
| 草稿机器数 | min(FactoryLimitsConfig.maxMachinesPerNode(), HARD_WIRE_ENTRIES) | 解码侧 |
| 回执 rejected 条数 | 32 | WandLimits.MAX_ISSUES_WIRE |
| 提交超时 | 5000 ms | WandLimits.SUBMIT_TIMEOUT_MILLIS |

### 8.3 链接快照

~~~java

    StorageMode mode,
    List<Link> storage,             // ME / 容器坐标

~~~

- 解码上限：nodes ≤ maxNodes、每节点 machines ≤ maxMachinesPerNode、机器总数 ≤ wireLimit(maxTotalMachines)、storage ≤ 16。
- 客户端整体替换，不合并；WandLinks 建 BlockKey → (nodeId, machineId) 与 nodeId → node 两张索引。不引入 revision：单线程生成 + 同一连接 TCP 有序 + 全量替换，已足够。
- 推送入口是新的 FactoryRuntime.markDirtyLinks(Factory)：先执行现有 markDirty（save + links.rebuild + requestReconcile），再对**该工厂**的在线归属者推快照（pushLinksTo(ServerPlayer, Factory)）。工厂由遍历 manager 得到，不靠玩家反查。
- markDirtyLinks 只在「会影响快照的结构写入」处调用：NodeLibraryService 的 publish、StorageLinkService 的锚点变更、FactoryObservationRunner 的类型迁移。规则 / provider / 名字 / 虚拟节点数据（NodeManager.dataChanged，搬运余量 flush 期间可能每 tick 触发）仍走 markDirty、不推快照——这条边界写进代码注释。
- 另外登录、换维度、打开终端时客户端主动发 FactoryLinksRequestC2S 请求一次。
- 不再轮询；不区分「摘要心跳」——单线程 + TCP 有序 + 全量替换，快照不会乱序。

### 8.4 requestSeq

- 客户端 WandCoordinator.nextSeq() 单调递增；草稿每次结构变更取新值，**提交前（含超时重试）也取新值**，避免「服务端已写库、回执丢了」时重试被 STALE_REQUEST 永久卡住。
- 服务端 per-player lastAcceptedSeq：**只有 commit 成功才推进**；失败不推进，同一份草稿可原样重试。
- requestSeq <= lastAcceptedSeq → STALE_REQUEST。
- WandCommitS2C 回带 seq；客户端只处理等于当前值或当前会话最后一次提交的回执，迟到包丢弃。
- 玩家下线时服务端清该玩家的记录（PlayerLoggedOutEvent），客户端登录时计数器归零。
- 预校验（WandOpenC2S）只读，不推进 seq。

### 9.1 入口与分层

~~~java
// factory/WandService.java（package-private，同包访问 NodeLibraryService / MachineLinkService）
final class WandService {
    WandCommitOutcome toggle(ServerPlayer player, BlockPos pos);

}
~~~

- 实现上 `ChainResult` / `OpenResult` 放在 `FactoryService` 作公共嵌套 record（网络层要直接消费），`WandService` 不 import `network`，方向仍是 network → factory。
- `commit` 由包 handler 先查 `FactoryGuiOpening.isWandMenu`，再调 `FactoryService.commitDraft`。
- 包 handler 只做「网络 record ↔ 内部数据」与「领域结果 → S2C」，不做业务判断。
- FactoryService 保留为静态装配点：新增 toggleMachine / chainMachines / openDraft / commitDraft 四个转发方法，替代 commitBinding / toggleMachines；deleteNodeById / toggleStorage / switchStorageMode 继续保留。

### 9.2 validate（顺序固定，只读）

1. 玩家主手是机器绑定杖。
2. 工厂存在且归属玩家（否则 NO_FACTORY）。
3. requestSeq > lastAcceptedSeq（commit 时；open 不查）。
4. 草稿非空（EMPTY_DRAFT）；nodeId == null 时 removed 为空。
5. nodeId != null → 节点存在（NODE_NOT_FOUND）；removed 每个 id 属于该节点。
6. added 内无重复块（DUPLICATE_BLOCK）。
7. 每个 added 方块：区块已加载（BLOCK_UNLOADED）、有方块实体、是有效机器（NOT_A_MACHINE，用 FactoryLinkFinder.isMachine）。
8. 占用两条都查：本工厂 machineAt 已存在 → BLOCK_CLAIMED；LinkGate.check(..., LinkRole.MACHINE) 被别人占 → BLOCK_CLAIMED。
9. 类型一致：新建草稿所有 added 同方块 id；编辑已有节点与 node.typeBlockId 相同（TYPE_MISMATCH）。
10. 上限：新节点查 maxNodes（LIMIT_NODES）；最终机器数 finalMachines 查 maxMachinesPerNode 与全工厂总量（LIMIT_MACHINES）。
11. finalMachines == 0：节点有规则 → DELETE_BLOCKED + HAS_RULES；有样板 → DELETE_BLOCKED + HAS_PATTERNS；否则允许删节点。
12. 1:1 toggle 的断开：节点 machineCount > 1 → MEMBER_NOT_REMOVABLE；规则或样板 → DELETE_BLOCKED。

输出 List<WandIssue>（空 = 通过）；rejected 截断 32，rejectedCount 给全量。

### 9.3 commit（原子写）

NodeLibraryService.Batch 不是事务，所以顺序固定：

1. validate 全量；有任何 issue 直接返回，不改任何状态。
2. 计算 finalMachines：新建草稿 base 不存在，按 0 计；编辑已有节点为 base.machineCount() - removed.size() + added.size()。
3. 构造 candidate：finalMachines == 0 → candidate = null；finalMachines > 0 → 新建时 candidate = new Node(randomUUID, null, typeId, new NodeIoGroup(), new NodeProvider(), machines, 0L)，编辑时 candidate = base 先逐个 withRemovedMachine、再逐个 withAddedMachine（withRemovedMachine 在只剩 1 台时返回自身，所以 0 台必须走 candidate = null）。
4. 交给 MachineLinkService.applyTopologyChange(factory, base, candidate, removedIds, player, batch)（§9.6）：
   - base == null（新建）：batch.add(candidate)，必须是 ADDED；
   - candidate == null（节点删除）：batch.remove(base.id())，返回 false → INVALID_REQUEST；
   - 其余（改节点）：batch.replace(candidate)，必须是 REPLACED。
5. batch.close() 之后：observations.refresh(block) 每个 added 方块（新增机器只有机器杖会产生，所以观测刷新留在 WandService）；被删机器的 nodeIoRunner.forget、节点删除 / 刷新已在 applyTopologyChange 内完成。
6. 任何返回值不是预期值 → INVALID_REQUEST 并记日志；close() 之前所有内存写都已按「先校验、后一次写索引」完成，不存在半改状态。
7. 成功后推进 lastAcceptedSeq，组装 WandCommitOutcome（added / removed / rejected）。

### 9.4 toggle（1:1）

1. 主手校验、工厂校验（NO_FACTORY）。
2. 目标区块已加载、方块实体存在、FactoryLinkFinder.isMachine。
3. LinkGate.check 被别人占 → BLOCK_CLAIMED。
4. 未绑定：candidate = Node.of(null, blockId, block)，以 base = null 调 applyTopologyChange（§9.6）；batch.add 非 ADDED 时按 NodeLibrary.Result 映射（FULL → LIMIT_NODES，DUPLICATE / CONFLICT → BLOCK_CLAIMED）；close 后 observations.refresh。
5. 已绑定：走 §9.2 第 12 条；通过则以 candidate = null 调 applyTopologyChange 删节点。
6. 返回 WandCommitOutcome（addedMachines / removedMachines 便于 HUD）。

### 9.5 chain

1. 主手 / 工厂 / 维度校验。
2. FactoryLinkFinder.machines(level, pos)（内部已含 128 / 4096 / 32 上限）。
3. LinkGate.of(manager).filter(factoryId, LinkRole.MACHINE, dimension, found)。
4. 只返回列表，不写库、不推快照。

### 9.6 删除副作用统一（B1）

现在 MachineLinkService.removeMachine（:78-101）把「退样板 + 移出节点库 + 拆虚拟节点 + 清执行器」写在一起，且部分删除也退样板。改成：

~~~java
// MachineLinkService
DeleteOutcome applyTopologyChange(Factory factory, @Nullable Node base, @Nullable Node candidate,
        Collection<UUID> removedMachineIds, @Nullable ServerPlayer receiver,
        NodeLibraryService.Batch batch);
~~~

- base == null：新建，batch.add(candidate)。
- candidate == null：删节点，batch.remove(base.id()) + nodeManager.removeNode + returnPatterns；样板退给 receiver（终端删节点路径）；绑定杖路径因 validate 已拒绝样板 > 0，实际不会退。
- 两者都非空：batch.replace(candidate) + nodeManager.refreshPatterns。
- candidate == null 时 removedMachineIds 允许为空：方法自己遍历 base.machines() 收集，保证终端删节点 / 1:1 断开都会逐个 forget。
- 每个被删机器 nodeIoRunner.forget(id)。
- deleteNodeById 与 WandService 都走它，删机器的副作用只有一套；规则 / 样板的拦截在 WandValidator，本方法不判规则。
- 新增机器的 observations.refresh 留在 WandService（终端没有新增机器的入口）。

### 9.7 状态与线程

| 状态 | 归属 | 生命周期 |
|---|---|---|
| lastAcceptedSeq | 服务端内存 Map<UUID, Long> | 玩家下线清 |
| 节点库 | 服务端存档 | 永久 |
| 链接快照 | 服务端生成，客户端只读 | 每次变更 / 请求重发 |

- 不新建线程、不建锁。
- open（预校验）与 commit 之间可能隔一个 tick，commit 必须重新 validate。

- 任意界面打开时不画（与现状一致）；草稿面板打开时世界框隐藏。
- 性能目标：100 台机器时帧率不低于重构前的 95%；4096 台时允许线框分块重建变慢，但不能每帧重建。

### 12.1 两条规则

1. **包名带 wand**：绑定杖相关代码无论在哪一层，包路径里都有 wand。

### 12.3 依赖方向

~~~text
client.wand.* ──► network.payload.wand.*, factory.wand.*（只读 record）
client.wand.screen.* ──► client.wand.*, menu.wand.*
menu.wand.* ──► 无业务依赖
network.payload.wand.* ──► factory.WandService / factory.WandValidator
factory.WandService ──► factory.wand.*, NodeLibraryService / MachineLinkService
~~~

- 服务端不引用 client.wand.*。
- factory 不 import network。
- network.payload.wand.* → factory 的方向与现有 FactoryBindingCommitC2S → FactoryService 一致，不新增分层例外；factory 不反向 import network。

### 12.4 为什么仍按层拆包

一个顶层 wand 包会把服务端与客户端混在一起，client.* 的 Dist 约束失效。按层拆 + 包名带 wand + 类名带 Wand，既保住分层，也能全局搜索定位。

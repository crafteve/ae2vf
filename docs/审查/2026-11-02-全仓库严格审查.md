## 审查结论

**改完再提交。** 范围：`src/main/java` 全部 190 个文件（33,025 行）、`docs/DECISIONS.md`、`AGENTS.md`。
走通的路径：`/idf machine add` → `FactoryService` → `MachineLibrary.add` → `markDirty` → `save()` + `links.rebuild` → 下一 tick `observe()` → `handleTransition` → `machineMissing`/节点可用性 → `MachineRunner` 门禁 → `GroupRunner` → `IoTransfer` → `MEStorage`。

一句话结论：**骨架是对的，护栏是缺的。** 三层分工、`IoTransfer` 唯一写路径、AEKey 身份、服务端权威都成立；真问题只有三件——配置写入口是「约定」而不是「方法」、两条扣减路径没有异常与退款护栏、巨型类和反向依赖让每次改动横跨 5–8 个类。

## [待确认]

- `RuleResolver.itemAccessible` 探面按「默认栈 / 规则样本 / 机器内变体」，实际搬运按仓库变体走；机器只收某种组件变体时可能落到错面。
- `MachineRunner` 每 tick 只要不是 `REJECTED` 就 `noteSuccess`，会解冻 `frozenFaces`；「面确凿不对 + 槽位周期性满」时熔断可能失效。
- `connectMachine` 用 `presence.kinds()`、`bindContainer` 用 `isAnyContainer`（多接受 legacy `Container`）：是否刻意「能当仓库不能当机器」。
- `FactoryPatternSlotActionC2S` 的 `QUICK_MOVE`：`Inventory.add` 返回 false 时若已部分写入，可能「部分进背包 + 原槽不删」。

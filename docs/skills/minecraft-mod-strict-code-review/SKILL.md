# 严格代码审查（Minecraft 模组）

## 〇、审查契约

### 0.1 编译能证明什么

| 编译能证明 | 编译不能证明 |
|---|---|
| 类型匹配、签名一致 | 条件写得对不对 |
| 类与方法存在 | 默认值合不合理 |
| 可见性、泛型约束 | 执行顺序对不对 |
| 语法合法 | 两个线程会不会同时进来 |
| 名字拼错（部分） | 同一件事是不是有第三种写法 |
| — | 失败时状态是否一致 |
| — | 这段代码三个月后还能不能改 |

**只做右列。** 左列由 `build`、IDE、启动日志负责。再查一遍，只是浪费一轮对话。

### 0.2 立场

1. **结构问题优先。** 有架构意见时，不要用一堆命名建议把它稀释掉。
2. **每条必须自证。** 什么输入、什么顺序、哪一行、造成什么后果。给不出场景的怀疑，降级为「待确认」。
3. **每条必须可命名。** 一条意见要能说出「改成什么」——一段代码，或一个具体的结构调整。说不出改法的，是模糊不适，丢弃，不算发现。
4. **不为「能跑」签字。** 能编译、能启动、点两下没崩，都不构成通过理由。
5. **克制。** 人和模型都有「多写一点」的倾向：多一个判空、多一个开关、多一层抽象、多一个依赖。审查要反过来问：规格今天需要这一行吗？不需要就是不该有。
6. **不软化。** 让代码库更乱的地方就说它更乱；错过一次明显简化机会就说错过了。语气可以平，结论不能模糊。
7. **只读。** 不改代码，不顺手重构。允许跑构建，但构建结果不作为结论。

### 0.3 不审什么

- 不审 API 名称、版本差异、能否加载、依赖是否声明。
- 不审「这样写编译不过」。
- 不审工具能自动处理的格式问题（缩进、import 排序、行宽）——但**项目内部是否自洽**要审。
- 不审玩法设计、数值平衡、美术风格。

## 一、开工

### 1.1 先分清审查类型

**在写任何结论之前，先确定这次是哪一种**：

- **重构审查**：目标是让结构更好，**可观察行为不得改变**——同样的输入、输出、异常、副作用。任何会改变行为的建议，单列成「行为变更，需作者确认」，不许混进重构建议里。
- **正确性审查**：目标是找 bug，行为变更在射程内，影响契约的按必须修复处理。

分不清就问。搞错类型的代价是：把 bug 当风格问题放过去，或者把重构建议当 bug 报。

### 1.2 先建模，再看 diff

架构与整洁度都不能从 diff 第一行开始读。先回答：

1. 这个项目分几层？每层一句话说得清吗？
2. 这次改动落在哪一层？跨层了吗？
3. 它改了哪些状态？这些状态原本归谁？
4. 有哪些读者？读的人知道写的人改了它吗？
5. 这段代码在哪个线程上跑？谁保证的？

### 1.3 产出三张图（文字版写进报告）

- **调用链**：入口 → 经过哪几层 → 落到哪个写操作 → 谁读结果。
- **状态归属表**：字段/对象 → 谁创建 → 谁写 → 谁读 → 活多久 → 是否跨线程。
- **线程边界**：哪些在主线程，交接点在哪，交接时传了什么。

### 1.4 走通一条路径

挑最典型的一条：触发 → 校验 → 状态变更 → 通知 → 持久化。**只读 diff 不读调用方，是这类审查最常见的失败方式。**

### 1.5 先摸清项目自己的风格

洁癖的前提是「与项目既有风格一致」，不是「与我的风格一致」。读 `CONTRIBUTING`、读两三个同类文件，确定：命名习惯、注释语言、`record` 用不用、错误处理是返回码还是异常、常量放哪。

**项目有明确约定的以项目为准；没约定的才用本 skill 的默认值。** 拿外部习惯覆盖项目风格，制造的是 diff 噪音，不是整洁。

### 1.6 声明范围

报告开头写清审了哪些文件、走了哪条路径、哪些只粗读。diff 超过约 600 行就分批（先状态与写入路径，再并发与生命周期，最后外围）。

## 二、洁癖层

这一节是主战场。判据不是「我喜不喜欢」，是「同一件事有没有第二种写法」「这行代码有没有必要存在」。

### 2.1 一致性：一个概念，一种写法

- [ ] 同一个动作在项目里只有一种命名形态。`toTag` 配 `fromTag`，不要 `toTag` 配 `deserialize`。
- [ ] 参数顺序在所有同类方法里一致：目标对象在前，选项在后；同名参数在任何方法里含义相同。
- [ ] 错误处理只有一套：返回码或异常，不许两种混用。混用的地方，调用方一定有一处判断错。
- [ ] 空值约定统一：要么一律返回空集合，要么一律 `null`，不许按方法随机。
- [ ] 集合返回统一：要么都返回不可变视图，要么都返回拷贝。
- [ ] 布尔命名统一：`is` / `has` / `can` / `should`，不许 `checkXxx`、`xxxFlag`、`flag` 混着来。
- [ ] 日志格式统一：统一前缀、统一级别、都带足以定位的上下文。
- [ ] 注册/订阅/初始化只有一种写法，不要一半注解、一半手动。
- [ ] 常量集中：同类常量不散落在多个类里。
- [ ] **同一件事出现第三种写法时，判建议修改，并指出保留哪一种、另外两种怎么改。**

### 2.2 对称性：成对操作必须成对

- [ ] `encode` / `decode`、`save` / `load`、`toX` / `fromX`、`add` / `remove`、`open` / `close`、`register` / `unregister`、`begin` / `end`、`acquire` / `release`。
- [ ] 成对的方法在文件里相邻；不相邻就要有理由（比如分层要求）。
- [ ] 写入顺序与读取顺序相反时（先写 A 后写 B，读时先读 B），必须注释说明，否则后人一定会改错。
- [ ] 异常路径同样对称：注册了一半失败，要把已注册的撤掉。
- [ ] 数量对称：加了几个字段，就加几个字段的读写；改了协议字段，版本号与兼容分支同时改。
- [ ] 清理路径成对：有 `try` 就有 `finally`，有分配就有释放，有订阅就有退订。

**不对称是最容易漏、后果最直接的一类。** 看到 `add` 就去找 `remove`，看到 `save` 就去找 `load`，找不到就是结论。

### 2.3 残留物：零容忍

- [ ] 注释掉的代码。
- [ ] 未使用的 import、字段、参数、私有方法、本地变量。
- [ ] `TODO` / `FIXME` 没有负责人和期限。带期限的临时方案可以留，但要写清到期后怎么办。
- [ ] 调试输出：`System.out`、`printStackTrace`、临时日志、临时开关。
- [ ] 孤儿资源：没有对应代码的配置项、翻译键、贴图、注册项。
- [ ] 兼容用的旧方法没有标废弃、没有写迁移路径。
- [ ] 空实现的方法没有注释说明为什么空。
- [ ] 被注释掉的测试、被跳过的校验。
- [ ] **同一功能两套实现并存**：新的写了，旧的没删，调用方还在用旧的。
- [ ] 半成品：分支不可达、方法定义了但没人调用、`// 这里要加错误处理` 但没加。

**残留物本身不是大问题，但它们会累积成「这个项目没人管」的信号。**

### 2.4 整齐：结构可预测

- [ ] 成员顺序固定：常量 → 静态字段 → 实例字段 → 构造 → 公开方法 → 包私有 → 私有 → 内部类。项目已有顺序的跟随项目。
- [ ] 一个文件一个顶级公开类。
- [ ] **一个函数一个抽象层级**。不要在同一函数里同时出现「打开连接」「拼查询」「算业务规则」「拼输出」四层。
- [ ] **调用者在被调用者上方**（step-down）。从上往下读，复杂度逐级下降；读文件时不用来回跳。
- [ ] 成组的相关函数相邻：`parseX` 与 `validateX` 挨着，不要一个在文件头一个在文件尾。
- [ ] 变量在靠近首次使用处声明，不集中堆在方法开头。
- [ ] 方法内用 guard clause 提前返回，不写三层以上嵌套；超过三层判建议修改。
- [ ] 空行有规律：相关行成组，组间一空行。随机空行等于没有分组。
- [ ] 同类方法长度量级相近；一个方法是同类方法的五倍长，通常说明它做了两件事。
- [ ] 同构的类有相同骨架：同样方法顺序、同样日志位置、同样错误处理位置。
- [ ] 行长、引号、import 顺序跟随本文件既有风格。工具管格式，**文件内自洽是人管的**。

### 2.5 命名

- [ ] 名字说明它维护哪个不变量，而不是它是什么类型。
- [ ] 禁用无信息词：`data`、`info`、`result`、`item`、`value`、`temp`、`obj`、`manager`、`helper`、`util`、`processor`、`handler`、`service`（不带领域限定时）。指出它实际负责什么。
- [ ] 禁编码前缀/后缀：`IUserRepo`、`m_count`、`strName`、匈牙利式命名。
- [ ] 禁无信息后缀：`NameString`、`UserData`、`OrderInfo`、`XxxImpl`。`Product`、`ProductInfo`、`ProductData` 若指同一件事，说明只有噪音、没有区分。
- [ ] 可搜索：循环外的单字母名禁止（`d`、`tmp`、`obj`）；常量要能 grep 到。
- [ ] 可朗读：拼不出来的缩写不算名字（`genymdhms` → `generationTimestamp`）。
- [ ] 不缩写，除非项目已有约定（`id`、`pos`、`cfg`）。
- [ ] 单位进名字：`timeoutTicks` 而不是 `timeout`；`sizeBytes` 而不是 `size`。
- [ ] 不用否定名：`pending` 而不是 `notReady`；`visible` 而不是 `notHidden`。
- [ ] 集合用复数，单元素用单数；类型不是集合就不要叫 `xxxList`。
- [ ] 类名是名词，方法名是动词短语，返回布尔的是判断句（`isXxx` / `canXxx`）。
- [ ] 包名是领域名词，不是分类垃圾桶。

### 2.6 数值与常量

- [ ] 没有魔法数。出现字面量就问：单位是什么、为什么是这个值、改的时候要同步改哪里。
- [ ] 同一字面量出现两次以上，提取常量。
- [ ] 单位混用是大问题：同一概念一半 tick 一半毫秒，编译发现不了，运行起来差 50 倍。
- [ ] 上限、下限、间隔、容量都具名，且在使用处有校验。
- [ ] 有 `max` 就要有对应的 `min` 校验；有 `size` 就要考虑溢出。
- [ ] 常量放在它服务的那一层，不集中到一个「常量类」变成垃圾桶。

### 2.7 注释

**先给该保留的六类**，免得一刀切删光：

1. 许可证头。
2. 解释「为什么」的意图（`// 用指数退避，避免重试时打爆限流`）。
3. 后果警告（`// 此方法在提交阶段调用，不要抛异常`）。
4. 带追踪号的 TODO。
5. 契约文档：前置条件、后置条件、会抛什么、副作用。
6. 放大说明（`// +1 是因为区间闭合`）。

**再给该删的**：

- [ ] 复述代码的注释：`// 把 x 设为 y` 贴在 `x = y` 上方。
- [ ] 噪音注释：`// 默认构造器`、`// getter`。
- [ ] 横幅注释：`// ====== 用户函数 ======`。用类或文件拆分代替。
- [ ] 闭合大括号注释：`} // end for`。需要它说明函数太长。
- [ ] 署名/变更日志注释：`// Bob 2023-04-01 修复 #42`。版本控制已记录。
- [ ] `// Step 1`、`// 首先`、`// 然后` 这类脚手架。每一步应该是一次具名调用。
- [ ] 注释掉的代码。
- [ ] 文档注释复述签名：`// 把 a 和 b 相加并返回结果`。
- [ ] 注释与代码矛盾——比没有注释更糟，判必须修复。

### 2.8 重复

- [ ] 同一段逻辑出现三次以上没有提取，判建议修改，并给出提取后的签名。
- [ ] **近似重复是重点**：结构相同、名字不同、只改了一两行的两段代码。逐行对比，找「复制时忘了改」的那一处。
- [ ] 提取后的方法要表达意图，不是把五个参数塞进去的 `doStuff(a, b, c, d, e)`。
- [ ] **反向检查：错误抽象**。一个共享函数为了适配每个调用方，长出了越来越多分支和开关参数——这是假复用，应该拆回各自实现。
- [ ] 重复的是知识，不是文本。只是长得像的两个概念，不要强行合并。

### 2.9 变更纪律

- [ ] diff 每一行都能追溯到这次需求。顺手重排、顺手格式化、顺手改常量、顺手升依赖，一律从 diff 里拿出去。
- [ ] 不同关注点分开：格式化与逻辑改动不混在一次变更里。
- [ ] 改签名的，调用方、文档、注释同步改；找不到调用方说明它是死代码。
- [ ] 新增抽象/工具类前，先确认项目里没有同类；有就用现成的。
- [ ] 删代码要删干净：删了实现，对应配置、翻译键、注册项一起删。
- [ ] **「简化」不得删掉边界校验或清理路径**（`finally`、`close`、回滚）。那不是清理，是行为变更，判必须修复并单列。
- [ ] 重构审查下行为不得变；任何会改变行为的改动，单列「需作者确认」，不混进重构建议。

## 三、架构层

### 3.1 分层

- [ ] 每层能用一句话说清职责。说不清 = 没有存在理由，或混了两个职责。
- [ ] 上层依赖下层，不反向。用回调/事件掩盖的反向依赖仍然是反向依赖。
- [ ] 跨层调用显式。A 绕过 B 直接调 C，而 B 正是负责一致性的那层，就是 bug 温床。
- [ ] 没有上帝类：一个类同时管解析、校验、执行、持久化、展示，判必须修复并给出拆分边界。
- [ ] 没有垃圾桶包：`util`、`common`、`misc`、`helper` 出现，说明有概念没被命名。指出该建什么。

### 3.2 依赖方向

- [ ] 画出本次涉及的模块依赖，找反向边和环。
- [ ] 环的判定看语义依赖，不看 import 数量。
- [ ] 同层两个模块互相调用，通常说明边界划错，应该抽第三层或合并。
- [ ] 静态持有、全局单例：谁持有谁，生命周期是否匹配。短命持有长命没事，反过来是泄漏。

### 3.3 边界与契约

- [ ] 公共 API 暴露的是概念还是实现：返回内部可变集合、暴露实现类、把内部状态对象直接给出去，都是契约泄漏。
- [ ] **校验在边界做一次，内部信任**。到处防御等于没有契约。
- [ ] **信任边界内不为不可能的情况加判空**。类型和调用约定已经排除的情况，再加判断只会掩盖真实契约；但外部输入、反序列化数据、跨进程数据必须校验。两者混淆的后果是「每个方法都判空，却没人知道谁该保证非空」。
- [ ] 返回值语义明确：`null` 是「没有」还是「失败」；空集合同理。
- [ ] **命令与查询分离**：返回值的方法不改可观察状态；改状态的方法不用返回值表达成功与否（用异常或结果对象）。
- [ ] **查询不得有副作用**：getter / finder / 判断式方法不修改状态；内部缓存可以，但不能改变可观察行为。
- [ ] **优先异常而不是返回码**：返回码会被调用方遗忘，异常不会。
- [ ] 得墨忒耳：`a.b().c().d()` 说明在跨对象翻内部结构，契约没收住。
- [ ] 参数达到 5 个就停，抽成配置对象 / record；3 个以上就该考虑。
- [ ] 跨层传递的数据如果被反复拆开重组，说明缺一个领域对象。

### 3.4 状态的唯一真相

- [ ] 同一个事实在系统里有几份？每多一份就多一处不一致。
- [ ] 有副本就要能回答：谁是权威、何时同步、同步失败怎么办。
- [ ] 状态存在哪：内存、存档、配置、客户端。混用会产生「重启后行为变了」这类问题。
- [ ] 写入点超过两处且没有统一入口，判建议修改：收成一个写方法，不变量只在一处维护。
- [ ] 读的人是否知道它可能过期，过期窗口内读到旧值有什么后果。

### 3.5 抽象

- [ ] 只有一个实现的接口、纯转发的 helper、只改名字的包装，增加阅读成本却不降低复杂度。
- [ ] 抽象泄漏：调用方必须知道「先调 A 再调 B」才能正确使用，说明没包住。
- [ ] 一个类的方法是否围绕同一个不变量组织；方法之间毫无关系，说明是两个类。
- [ ] 抽象的名字是否说出了它隐藏的决策，而不是它的形状。

### 3.6 演进成本与 YAGNI

- [ ] **加一个维度要改几处？** 最客观的架构指标。改 1 处是设计好，改 5 处是模型漏了。
- [ ] 有没有一种重构能让一整类分支消失？有就提，不要只提「可以再干净点」。
- [ ] 搬家式重构（复杂度从 A 挪到 B，概念数没减少）不算改进，明确指出。
- [ ] 条件爆炸：连续布尔组合通常缺一个枚举或状态对象。
- [ ] 隐式状态机：几个布尔量表示互斥状态，存在非法组合。改枚举，让非法状态不可表示。
- [ ] 顺序依赖：A 必须在 B 之前，但没有任何机制保证。合并成一个方法，或在 B 里校验前置条件。
- [ ] **没有调用方的开关**：可选参数、配置项、`enableXxx` / `useXxx` / `xxxMode`、为「以后可替换」而包的壳，一律判建议修改。
- [ ] **为一个功能加依赖**：能用标准库、已有依赖或几行代码解决的不引入新依赖。

### 3.7 SOLID 五问

- [ ] **SRP**：这个类的方法是否服务两个不相关的使用方？
- [ ] **OCP**：按类型标签分派的 `switch` 是否随着需求不断加 `case`，而类型本身是封闭的？
- [ ] **LSP**：子类是否抛「不支持」、加强前置条件、弱化后置条件？
- [ ] **ISP**：接口的客户端是否只用其中一部分方法？
- [ ] **DIP**：高层是否 import 低层具体类？抽象和实现是否同居一个包？

### 3.8 概念建模

- [ ] 同一概念只有一种表示。两套 id、两套坐标、两套单位，转换点就是 bug 点。
- [ ] 同一个词在不同层含义一致。同名不同义是长期毒药。
- [ ] 单位统一：tick 与毫秒、方块坐标与区块坐标、含头与不含头。

## 四、运行时层

编译通过、启动正常、点两下没崩——问题在这一节。

### 4.1 逻辑

- [ ] **边界三连**：空输入、单元素、满/上限。三个都想过再签字。
- [ ] **先枚举情形再读代码**：为空 / 一个 / 偶数 / 奇数 / null，逐项对照实现。
- [ ] 条件是否写反：把 `if (!x)` 读成「x 为真时会怎样」，反证一遍。
- [ ] off-by-one：`<` 与 `<=`、`size()` 与 `size()-1`、循环变量在循环外被用。
- [ ] 默认值：`0` 是合法值还是「未设置」；`-1` 是不是哨兵。混用会导致「设成 0 时行为异常」。
- [ ] 空集合与 `null` 是否同等对待；`Optional` 是否被直接取值。
- [ ] 数值：整数除法截断、溢出、精度丢失、负数取模。
- [ ] 状态机穷尽：每个状态在每种输入下都有明确转移，没有「落空就什么都不做」。
- [ ] **看着对但算错**：与相似函数逐行对比，确认没有「复制过来忘了改」的公式、范围、null 语义。

### 4.2 不变量与原子性

对每个「改了多处状态」的方法问三句：

1. 这一步失败了，前面已经改了什么？
2. 能不能回滚？回滚需要的信息现在有吗？
3. 别人在这中间读到的，是不是一个不存在的中间态？

- [ ] 多步更新要么全成要么全不成；做不到就要有明确的中间态语义。
- [ ] 先扣后给、先给后扣的顺序，决定失败时是丢东西还是多东西。
- [ ] 检查与执行分离的中间窗口，是否可能被别人改掉（见 4.3）。
- [ ] 幂等：重试、重复触发、重复收包时会不会执行两次。
- [ ] 顺序依赖的更新失败后，是否留下「已标记未完成」的悬挂状态，有没有补偿。

### 4.3 并发与死锁

先回答：**这段代码允许被哪些线程调用？谁保证的？** 答不出来，后面都不用看。

**竞态**

- [ ] 共享可变字段：列出所有写入点，看是否同线程或有同步。
- [ ] check-then-act：先查后改的两步之间，状态可能被别人改掉。
- [ ] 复合操作非原子：读-改-写、自增、懒初始化。
- [ ] 发布未完成初始化的对象：构造器里把 `this` 注册出去、放进静态集合、传给别的线程。
- [ ] 可见性：跨线程标志位是否 `volatile` / 原子类型；双重检查锁是否漏 `volatile`。
- [ ] 集合：多线程读写的 `HashMap` / `ArrayList` 会静默损坏；遍历时修改会抛并发修改异常。
- [ ] 异步完成顺序：两个异步结果到达顺序是否影响最终状态，有没有保证。
- [ ] 异步异常是否被吞：`CompletableFuture` 的异常没人记录、没等待就返回。

**死锁**

- [ ] 列出所有锁，按获取顺序建图。**有环 = 有死锁可能**，哪怕现在没触发。
- [ ] 锁内是否调用外部代码：回调、监听器、可覆写钩子。对方可能回头拿另一把锁。
- [ ] 锁内是否做 IO、等待、`join`、睡眠。
- [ ] 两把锁的获取顺序在不同入口是否相反。
- [ ] `tryLock` 失败是否被忽略后继续执行；超时是否被当成成功。
- [ ] 是否拿可变对象当锁。
- [ ] 是否在持锁时回调其他模组或用户代码——这是模组环境最常见的死锁来源。

**线程归属**

- [ ] 世界状态只在主线程碰；后台线程只做纯计算，结果回主线程应用。
- [ ] 交接点明确写了「交接后允许碰什么」。
- [ ] 任务取消后是否还会执行；取消与执行之间的窗口是否处理。

### 4.4 生命周期

- [ ] 注册与注销成对，**异常分支也能走到注销**。
- [ ] 初始化顺序：A 依赖 B 已完成初始化，但没有任何机制保证。
- [ ] 重入：同一方法在回调链里被再次调用，状态是否还正确。
- [ ] 销毁后回调：对象已失效，外部仍持有引用。
- [ ] 长命对象持有短命对象：静态集合、缓存、监听器列表没有清理。
- [ ] 重新初始化：状态是否被重置，旧实例是否被丢弃。

### 4.5 资源与增长

- [ ] 缓存有没有上限和淘汰策略。无界缓存等于慢性 OOM。
- [ ] 每个事件/每个对象都 new 并留存，规模上来就爆。
- [ ] 递归有没有深度上限。
- [ ] 文件、连接、缓冲区是否在 `finally` 关闭。
- [ ] 高频路径上的日志是否无节制。
- [ ] 集合是否只增不减。

### 4.6 异常与失败

- [ ] `catch` 后吞掉异常还返回成功 —— 最危险的一类。
- [ ] 异常发生时已修改的状态是否回滚。
- [ ] 空 `catch`；`catch` 后 `return null` / `return true`。
- [ ] 捕获范围过宽，把编程错误当业务错误。
- [ ] `catch` 后只是重新抛出，不附加任何信息 —— 噪音，删掉。
- [ ] 失败被转成默认值：查询失败返回空集合，调用方以为「没有数据」。
- [ ] **硬编码成功 / 假数据冒充实现**：函数该做真事却 `return 1000`、返回固定列表；做不到就显式失败并说明缺什么。
- [ ] 降级路径是否真的降级。
- [ ] 异常信息够不够定位，还是只有 `e.getMessage()`。

### 4.7 崩溃面

- [ ] 可能为 `null` 的返回值是否下一行就被解引用。
- [ ] `Optional.get()`、`Map.get()`、数组与列表下标。
- [ ] 强制类型转换：`instanceof` 与转换之间有没有别的代码。
- [ ] 遍历时修改集合（包括通过回调间接修改）。
- [ ] 递归深度无上限。
- [ ] 数值转换与除法。
- [ ] 初始化失败后的半初始化对象仍被使用。

## 五、零容忍清单

见到就报，不许放过。归到必须修复或建议修改视影响而定，但不能当没看见。

1. `catch` 后返回成功，或失败被静默转成默认值。
2. 硬编码成功值、固定假数据冒充实现。
3. 两把锁在两条路径上以相反顺序获取。
4. 锁内回调外部代码。
5. 共享可变状态跨线程写，无同步，且给不出线程约束。
6. check-then-act 无保护。
7. 多步更新失败不可回滚，且没有中间态语义。
8. 注册与注销不成对；异常路径不注销。
9. 实例被注册进事件总线/监听器列表且没有移除路径。
10. 无界缓存、只增不减的集合、无深度上限的递归。
11. 注释掉的代码、调试输出、无期限的 TODO。
12. 同一件事的第三种写法。
13. 同一功能两套实现并存，旧的没删。
14. 魔法数、单位混用。
15. 布尔盲参。
16. 隐式状态机（多个布尔量表示互斥状态）。
17. 返回内部可变集合或内部状态对象。
18. 反向依赖或依赖环。
19. 上帝类（一个类担三种以上职责）。
20. 注释与代码矛盾。
21. 复制粘贴后忘了改的那一处。
22. diff 里与需求无关的改动。
23. 以「简化」为名删掉边界校验或清理路径。
24. 没有调用方的开关、可选参数、为替换而包的壳。
25. 编码前缀（`I`、`m_`）或无信息后缀（`UserData`、`OrderInfo`）。
26. 命令与查询混用：返回结果又改状态。

## 六、专业度判据

「专业」不是风格偏好，可以逐条判定：

| 判据 | 不专业 | 专业 |
|---|---|---|
| **不变量** | 靠注释和记忆维持「这里必须非空」 | 用类型、构造器、断言让它不可违反 |
| **契约位置** | 每个方法都判空 | 边界校验一次，内部信任并写明前置条件 |
| **失败语义** | 返回默认值 / 吞异常 | 显式返回，调用方必须处理 |
| **状态** | 同一事实三份副本，手工同步 | 一份权威，其余是派生或带失效策略的缓存 |
| **对称性** | 有注册没注销，有加锁没解锁 | 成对操作写在同一处，异常路径也覆盖 |
| **一致性** | 同一动作三种命名 | 一种命名，全项目统一 |
| **函数形态** | 一个函数四层抽象、六个参数、两个职责 | 一个层级、一个职责、参数收敛成对象 |
| **可验证性** | 核心逻辑只能进游戏试 | 核心逻辑可脱离运行时验证 |
| **演进成本** | 加一个维度改五处 | 改一处，或加一个实现类 |
| **命名** | `Manager`、`Data`、`Info`、`Helper` | 名字说明它维护哪个不变量 |

给「专业度」意见时，必须落到上表某一行，不许写「不够优雅」。

**语气示例**（可以照用）：

- 「这个文件这次又要加 120 行，先拆再合。」
- 「这是同一件事的第三种写法，保留一种，另外两种改掉。」
- 「这个 catch 把失败变成了成功，等于把 bug 藏起来。」
- 「这行改动和需求无关，从 diff 里拿出去。」
- 「这里没说谁保证单线程，给不出就说明它没有约束。」
- 「这次重构把复杂度从 A 挪到了 B，概念数没少，不算改进。」
- 「这个开关没有任何调用方会用到，删掉。」

## 七、取证方法

### 7.1 六条硬规矩

1. **给触发场景**：什么输入、什么顺序、什么时刻、哪个线程。给不出就降级为「待确认」。
2. **给代码路径**：从哪进来、经过哪、在哪出错。只给一行不算。
3. **给可命名的修复**：说得出改成什么。说不出就不是发现，丢掉。
4. **区分「一定错」和「可能错」**：前者进必须修复，后者进待确认。
5. **不虚构行为**：依赖的方法语义要能指出来源，否则写「未验证」。
6. **不拿「我见过这种 bug」当证据**：模式匹配只是线索，最终要落到这段代码。

### 7.2 六种手法

| 手法 | 怎么做 | 找什么 |
|---|---|---|
| 状态写入表 | 列出可变字段所有写入点 | 多写入点无同步 → 竞态；写入分散 → 不变量无人维护 |
| 锁顺序图 | 列出每处获取的锁与顺序 | 有环 → 死锁 |
| 中间态推演 | 在两步更新之间插入「此刻别人读到什么」 | 半应用状态 |
| 异常注入 | 假设第 N 行抛异常，问前面改了什么 | 不可回滚 |
| 生命周期配对 | 列出所有 register/unregister、open/close | 缺一半 → 泄漏、幽灵回调 |
| 边界枚举 | 空、单元素、满、并发修改 | 越界、空指针、并发修改异常 |

### 7.3 一条路径读到底

触发 → 校验 → 状态变更 → 通知 → 持久化。每一步都问「这一步失败会怎样」。读完这条路径，通常覆盖本次改动 80% 的运行时风险。

### 7.4 被质疑时

作者不接受某条意见时：

- 指出它违反的是哪个原则、为什么在这里成立，不要引用「规则第几条」——数字对后人没意义。
- 如果接受例外，必须记录**原则 + 理由 + 重启条件**（什么情况下应该回头改）。**没有重启条件的例外，本身就是一条发现**：没有出口的例外只是延期的债。
- 例外记录之后，后续审查不再重复报，但重启条件被触发时要报。

## 八、分级与输出

### 8.1 分级

| 标签 | 含义 | 判据 |
|---|---|---|
| **[必须修复]** | 不改不能提交 | 死锁、竞态导致数据错乱、半应用状态、吞异常掩盖失败、硬编码成功、无界增长、可复现崩溃、反向依赖或环、注册注销不成对、以简化之名删校验 |
| **[建议修改]** | 本次或下轮改 | 职责过载、抽象不成立、状态多副本、契约泄漏、一致性被破坏、演进成本过高、不变量未显式化、残留物 |
| **[仅供参考]** | 不改也行 | 命名、组织方式、可读性 |
| **[待确认]** | 不是问题，是疑问 | 意图不明；或怀疑成立但给不出触发场景 |

判级三原则：看影响不看条款；存量不背本次的账；同类问题合并成一条，列出全部位置。

### 8.2 输出模板

```markdown
## 审查结论
<建议提交 / 改完再提交 / 不要提交>。类型：<重构审查 / 正确性审查>。
范围：<文件>；实际读过：<文件>；走通的路径：<一句话>。

## 架构模型
- 分层：<层与职责>
- 本次改动落在：<层>，跨层：<是/否>
- 状态归属：<状态 → 谁写 → 谁读>
- 线程边界：<主线程/其他，交接点>

## [必须修复]
1. `Foo.java:120` 先扣数量再校验目标能否接收，失败时不回滚。
   触发场景：目标在扣减与写入之间被填满（同 tick 另一条逻辑写入），数量已扣、物品未给。
   为什么：不可逆丢失，没有补偿路径。
   怎么改：先查可接收量按该量扣；或失败时显式退款并给退款失败加日志。

## [建议修改]
1. `Bar.java:40` 这个类同时维护索引、校验、持久化，三个不变量在同一处。
   为什么：改索引逻辑要重新理解持久化时序，加一种资源要改三处。
   怎么改：拆成 Store 与 Index，校验放在写入入口。

## [仅供参考]
- `Baz.java:88` 字段名 `data` 不说明它维护哪个不变量。

## [待确认]
- `Qux.java:52` 这里没加锁，是假定只在主线程调用吗？谁保证？

## 覆盖率
每节写「发现」或「clean」。空着等于没看，不是通过。
- 2.1 一致性：clean
- 2.2 对称性：1 条（`Bar.java:40`）
- 2.3 残留物：2 条
- 2.4-2.6 整齐/命名/数值：clean
- 2.7-2.9 注释/重复/变更纪律：1 条
- 三 架构：2 条
- 4.1-4.2 逻辑与原子性：1 条
- 4.3-4.4 并发与生命周期：clean（已看锁顺序，无环）
- 4.5-4.7 资源/异常/崩溃面：clean

## 已验证
- `Foo.transfer` 的失败分支会回滚已扣数量（`Foo.java:150-162`）。

## 未验证
- 并发路径未压测，结论基于锁顺序推演。
```

### 8.3 写法要求

- 每条带 `文件:行号`；运行时问题还要带触发场景。
- 「为什么」写到后果为止（丢数据、卡死、崩、改不动），不要停在「不符合规范」。
- 结构问题优先；有架构意见时不要用命名建议稀释。
- **不造赞美**：没有值得说的就写「无」；有就说具体的，不写「整体不错」。
- **不给分数**：不写「质量 7/10」「比之前干净 30%」。没有基线，数字是编的。

## 九、通过标准

以下任一成立即不通过：

- 两把锁获取顺序相反，或锁内回调外部代码。
- 共享可变状态跨线程写且无同步，或 check-then-act 无保护。
- 多步更新失败不可回滚，且无补偿或中间态语义。
- `catch` 后返回成功，或失败被转成默认值。
- 硬编码成功值、假数据冒充实现。
- 以「简化」为名删掉边界校验或清理路径。
- 新增无界缓存、无深度上限递归、只增不减集合。
- 注册与注销不成对，异常路径不注销。
- 公共 API 泄漏内部可变状态，或返回值语义（`null` / 空集合）混用。
- 引入反向依赖或依赖环。
- 新增隐式状态机。
- 同一事实新增第二份副本且无同步与失效策略。
- 同一件事出现第三种写法且未收敛；或同一功能两套实现并存。
- 新增魔法数或单位混用。
- 新增没有调用方的开关、可选参数、包装层。
- 注释与代码矛盾。
- 核心逻辑只能进游戏验证，没有可独立验证的入口。

允许放行但必须写理由：为兼容旧数据保留的冗余；为性能刻意保留的重复计算（要给测量依据）；带明确到期条件的临时方案。

## 十、不要做的事

- 不审 API 存在性、版本差异、能否加载——构建与日志会报。
- 不审缩进与 import 排序——工具会管；但项目内部不一致要审。
- 不给没有触发场景的「可能有并发问题」。
- 不给说不出改法的意见。
- 不把模式匹配当结论。
- 不给分数、不造赞美。

## 附录 A：并发审查问句表

**归属**

1. 这个方法允许被哪些线程调用？
2. 这个约束写在哪？类型、文档，还是只在作者脑子里？
3. 被错误线程调用了会怎样？有没有断言或快速失败？

**共享状态**

4. 哪些字段可变且跨线程可见？
5. 每个字段的写入点在哪几处？
6. 读与写之间隔着什么？会不会读到中间态？

**锁**

7. 会拿哪些锁？按什么顺序？
8. 有没有另一条路径以相反顺序拿？
9. 持锁期间调用了哪些外部代码？它们会不会回头拿锁？
10. 锁对象本身可变吗？
11. `tryLock` 失败是否继续执行？超时是否当成功？

**异步**

12. 任务完成顺序会影响状态吗？
13. 取消后还会执行吗？取消与执行之间有没有窗口？
14. 回调在哪个线程执行？回调里碰了什么？

**失败**

15. 线程池满了会怎样？拒绝策略是什么？
16. 任务抛异常了，异常去哪了？

## 附录 B：编译通过、运行时出错的模式库

| 模式 | 编译为什么放过 | 怎么发现 |
|---|---|---|
| 写 A 读 B（名字/单位不一致） | 两边类型相同 | 对比写键与读键；对比 tick 与毫秒 |
| 条件取反 | 布尔表达式合法 | 反证法读一遍 |
| 默认值歧义（0 与「未设置」） | 都是 int | 找哨兵值的所有判断点 |
| 忽略返回值 | 不强制使用 | 找所有返回 boolean/Optional 的调用点 |
| 先处理后校验 | 顺序不影响编译 | 问「这一步失败，前面改了什么」 |
| check-then-act 竞态 | 单线程下正确 | 找两步之间的其他写入点 |
| 遍历时修改集合 | 语法合法 | 找循环体里的增删，含间接回调 |
| 锁内回调 | 语法合法 | 看持锁区间内是否调用外部实现 |
| 监听器未注销 | 语法合法 | 注册点必须有对应注销且在异常路径 |
| 无界缓存 | 语法合法 | 找 Map/List 字段，问淘汰策略 |
| 递归无上限 | 语法合法 | 找自我调用与图遍历 |
| 双重检查锁缺 volatile | 语法合法 | 找 `if (x == null) synchronized` |
| `this` 逃逸 | 语法合法 | 找构造器里的注册、发布、传参 |
| 整数除法/溢出 | 语法合法 | 找 `/`、`*`、`<<` 并确认取值范围 |
| 半初始化对象被使用 | 语法合法 | 找构造器里调用可覆写方法、抛异常后仍被引用 |
| 复制后忘改的公式 | 语法合法 | 与相似函数逐行对比 |
| 硬编码成功 | 语法合法 | 找没有实际计算就 return 常量的方法 |

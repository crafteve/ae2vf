# 20-IO 执行层命名与职责收敛

> 状态：讨论中
> 最后更新：2026-11-12
> 目标：确定执行层内部的命名、职责边界与「机器侧读写抽象」的唯一选择，作为下一轮重构的计划输入。

【用户已确认】2026-11-12：**探面器独立成类**，名字用 `IoFacePick`，与执行器并列；Planner 不再直接扫面。

【用户已确认】2026-11-12：Planner 是对**单条规则**的规划（择时、顺序、预算）；Runner 是对**表单**的遍历执行。`PassiveIoRunner` 改名 `PassiveRunner`，与 `PassivePlanner` 成对。

【用户已确认】2026-11-12：`Ledger` 的命名要能看出归属分析器。

【用户已确认】2026-11-12：「单元」这个词太模糊，看不出来是什么，必须改名。

【用户已确认】2026-11-12：`TransferStats` 并入分析器，不再单独成类。

【用户已确认】2026-11-12：`IoForm` / `IoUnit` / `IoUnitKey` 命名重复包名、可合并；`Io` 前缀在 `io` 包内一律去掉。

【用户已确认】2026-11-12：一次搬运任务叫 **IoJob**（不用 RuleJob，因为主动 IO 没有规则概念，但复用同一个 IoJob）。

【用户已确认】2026-11-12：`Ledger` / `Conclusion` 作为分析器的嵌套类型（`Analyzer.Ledger` / `Analyzer.Conclusion`），归属由名字可见。

【用户已确认】2026-11-12：**模糊规则的流程是**——规划器发现这条规则要搬模糊物品 A → 规划器调用「变体查询器」查到有 a 个变体 → 规划器按上限选前 8 个 → 规划器给执行器下 8 条搬运指令。规划器不直接读仓库。

【用户已确认】2026-11-12：**查询器与执行器、探面器是同一类组件**（都是执行侧的只读/只写能力），规划器只做决策并调用它们。

【用户已确认】2026-11-12：变体查询器命名 `IoVariantPick`，与 `IoFacePick` 同后缀；`Pick` 后缀已写入 AGENTS 命名表（执行侧只读查询器）。

## 关键发现（Agent 实测）

【Agent 建议·未确认】`appeng.helpers.patternprovider.PatternProviderTarget` 只有 `insert` 与 `containsPatternInput`，**没有 `extract`**（javap 实测 19.2.10）。它内部是 `CompositeStorage`（MEStorage）+ 匿名包装，只对外暴露单向写入。

【Agent 建议·未确认】`MEStorage` 本身有 `insert` / `extract` / `getAvailableStacks`，且 AE2 通过 `ExternalStorageStrategy` 把 NeoForge 的物品 / 流体 / FE 抹平。Applied Flux 已注册 `FEExternalStorageStrategy`（jar 内实测），因此 FE 走 AE2 抽象是通的。

【Agent 建议·未确认】结论：若只保留一套机器侧读写抽象，应统一到 **MEStorage**，而不是 `PatternProviderTarget`（缺 extract），也不是自写的三个适配器（功能覆盖更窄、重复实现槽位扫描）。

## 待定

【用户想法·待确认】用户倾向自己写适配器、不用 `PatternProviderTarget`；与上面的 MEStorage 结论需要二选一。

【Agent 建议·未确认】「单元」改名候选：`RuleJob`（机器 × 规则 × 方向的一次搬运任务），身份用 `RuleJob.Key`。

【Agent 建议·未确认】`Ledger` 归属写成嵌套类型：`Analyzer.Ledger` / `Analyzer.Conclusion`，包内不再有独立的 `IoLedger` / `UnitDigest`。

【Agent 建议·未确认】模糊规则 = 忽略物品组件；AEKey 的相等性包含组件，MEStorage 没有「按注册名匹配任意组件」的接口，所以执行时必须先枚举同注册名的具体 key（变体），再逐个搬；「变体名额」是每 tick 枚举/尝试的上限，属于预算，不是规则语义。

## 机器侧统一到 MEStorage（已确认）

【用户已确认】2026-11-12：机器侧读写统一到 `MEStorage`，删掉自写的三个适配器与 `PatternProviderTarget` 包装。

依据（Agent 实测 AE2 19.2.10）：`PatternProviderTarget` 只有 `insert` + `containsPatternInput`，**没有 `extract`**；`MEStorage` 有 `insert` / `extract` / `getAvailableStacks`；AE2 通过 `ExternalStorageStrategy` 把 NeoForge 能力抹平，Applied Flux 已注册 `FEExternalStorageStrategy`（jar 内实测），化学品同理。

【Agent 建议·未确认】目标结构（io 包）：

- 数据：`Form`（内嵌 `Entry` / `Entry.Key`）、`IoJob`、`Reason`、`DispatchOrder`、`DispatchQueue`、`DispatchContext`
- 规划：`PassivePlanner`、`ActivePlanner`
- 驱动：`PassiveRunner`、`ActiveRunner`
- 查询：`IoFacePick`、`IoVariantPick`
- 执行：`TransferExecutor`、`Transfer`（MEStorage ⇄ MEStorage，双向对称）
- 分析：`Analyzer`（内嵌 `Ledger` / `Conclusion`，吸收 `TransferStats`）

删除：`ResourceAdapter` / `ItemAdapter` / `FluidAdapter` / `EnergyAdapter` / `ItemVariantIndex`（并进 `IoVariantPick`）/ `IoUnit` / `IoUnitKey` / `IoLedger` / `UnitDigest` / `LedgerAnalyzer` / `TransferStats` / `IoResult` / `IoSide`。

【Agent 建议·未确认】必须进游戏验证的五点：

1. 只提供无向能力、不提供分面能力的机器：改后逐面可能拿不到存储，必要时保留「无向兜底」。
2. FE 探面模拟量沿用 1000（Mekanism 的 FE↔J 截断）。
3. 抽取顺序由 AE2 包装决定，与现在的「未满堆优先」不同（数量不受影响）。
4. 化学品会从「搬不动」变成「可搬」，需确认界面/JEI 是否跟得上。
5. 阻塞判定用 `getAvailableStacks` 自算，需与 AE2 的 `containsPatternInput` 语义对齐。
## 命名与执行顺序（2026-11-12 第二轮确认）

【用户已确认】2026-11-12：查询组件命名 `FacePick` / `VariantPick`（不在 `io` 包内重复 `Io` 前缀）。

【用户已确认】2026-11-12：**建 MEStorage 归 `PortResolver`**（按面懒建、按机器缓存）；`FacePick` 只决定用哪个面，不建存储。

【用户已确认】2026-11-12：执行只保留 `Transfer` 一个类（静态事务，双向），去掉 `TransferExecutor`。

【用户已确认】2026-11-12：每 tick 执行顺序 **回收 → 主动投递 → 被动**（主动先兑现承诺，被动最后补料，避免被动先塞满机器）。

【用户已确认】2026-11-12：`pushPattern` 只做「校验 + 拆份数 + 入队」，**不选面**；选面移到投递阶段。

【用户已确认】2026-11-12：不再保留「无向兜底」（MEStorage 已足够成熟）；FE 探面沿用 1000；抽取顺序由 AE2 决定可接受；化学品可搬但界面兼容先不做。

【Agent 建议·未确认】阻塞判定说明：现在用 AE2 的 `containsPatternInput`（内部就是拿该面清单与样板输入求交集）；改后自己 `getAvailableStacks` 拿清单，再与去组件的 `patternInputs` 求交集，语义一致。
## 第三轮确认（2026-11-12）

【用户已确认】2026-11-12：`PassivePlanner` **不做「同侧规则按游标轮转排序」**。同机规则互相挤占的问题，后续用「规则执行限制」解决。

【用户想法·待确认】2026-11-12：「规则执行限制」= 玩家给每条规则配置「维持数量」，让规则 A 不会占满机器导致规则 B 永远跑不了。属于后续功能，不在本次重构范围。

【用户已推翻】2026-11-12：Agent 的「规划器只判到点与名额、把 Pick 留给 Runner」是错的。**规划器必须自己调用 Pick**，产出可直接执行的 Job（含面与具体资源 key）；执行器只执行，不再查询。跨轮记忆仍然全部在 `Analyzer.Conclusion`，规划器本身不持有跨轮状态。

【用户已确认】2026-11-12：负责「建 MEStorage」与负责「搬运」都属于**执行**，用同一个后缀；`Pick` 只负责查，两者分开。

【用户已确认】2026-11-12：`Transfer` 必须区分「从源搬」与「凭空补」，命名定为 `move` / `fill` / `refund`。

【用户已确认】2026-11-12：执行侧两个类命名 **`PortExecutor`**（建 MEStorage）与 **`IoExecutor`**（搬运：move / fill / refund）；查询侧仍是 `FacePick` / `VariantPick`。

【用户已确认】2026-11-12：「规则执行限制」记为后续需求，不在本次重构范围。

## 需求总览（2026-11-11）

**一句话**：把 IO 重构成「一条带时钟的流水线」——观测层只负责知道世界，配置层只负责记录玩家意图，执行层每 tick 读这两份事实、排出这一 tick 该干的活、机械执行、记账，分析器把账压成结论供下一 tick 使用；主动与被动共用同一个机器写入口。

**必须满足的六条**：

1. **每 tick 两段**：准备（观测 → 认仓库 → 机器状态）→ 执行（回收 → 队列 → 被动）。
2. **两个真相 + 一个视图**：机器状态、执行状态是真相（存）；节点状态是视图（读时拼）。
3. **一张原因枚举**：所有「这一轮为什么不搬」收敛成它，界面直读，不再散落 return / continue / false。
4. **两个规划器，一个执行器**：被动规划器（tick）、主动规划器（AE2 同步 + tick）；执行器无跨轮记忆，只做「给我规则和策略，我搬一次」。
5. **主动与被动共用**：机器侧写入口（选面 / 模拟 / 写入 / 退款）、账本、分析器、历史结论。
6. **表单是唯一工作清单**：不在表单上的单元，执行层根本不认识它——「不可用 / 被删 / 未加载」在生成表单时就已过滤。

**不动的**：搬运事务不变式、存档兼容、AE2 接口、规则归节点、节点可用性定义、包依赖方向。

**本轮的取舍**：配置层确定要重构但暂缓；不做仓库变化表（几毫秒延迟不值得每 tick 摸世界）；执行层走 tick，配置层走事件。

## 三种状态（已确认不要混）

【Agent 建议·未确认】判据不是「分成三个模块」，而是分清哪些是真相、哪些是视图：

| 状态 | 来源 | 变化频率 | 是真相还是视图 |
|---|---|---|---|
| 机器状态 | 世界事实 + 配置事实 | 低（方块拆了、区块加载） | 真相，存 |
| 执行状态 | 执行层自身（睡眠、堵塞、拒收、最近搬动） | 高（每轮都可能变） | 真相，存，归执行层 |
| 节点状态 | 成员机器状态的聚合 | 跟随成员 | 视图，不存，读时拼 |

【Agent 建议·未确认】机器状态只回答「这台机器在世界上存在吗、加载了吗」，不回答「它这轮搬没搬动」。

【Agent 建议·未确认】睡眠、堵塞、拒收、搬运计数全部属于执行状态，不进机器状态；执行状态与机器状态分两张表，因为变化频率差一个数量级，混在一起会互相污染（执行层每轮写全表，把低频状态也一起改）。

## 执行层内部分角色（已确认方向）

【用户已确认】2026-11-11：执行层不是一个「执行器」，而是「规划器 + 执行器 + 账本 + 分析器」。

【用户已推翻】「这一轮一点都没搬动 → 定个 200 tick 的闹钟」：一轮空转不足以推出结论，也不该由执行器自己拍。

【Agent 建议·未确认】四个角色：

```
执行层
 ├─ 规划器 Planner
 │    · 读：账本历史
 │    · 写：排期表（谁、什么时候再跑）
 │    · 决策依据：连续成功 / 连续失败时长、连续被拒次数
 │    · 主动侧的回收节奏（5 tick / 退避 20→128）也归这里，不再散落常量
 ├─ 执行器 Executor
 │    · 读：排期表（到点没）、规则、机器状态
 │    · 写：账本（新增一行）
 ├─ 账本 Ledger
 │    · 每行：tick、机器、规则、结果、搬了多少
 │    · 有界环形，只保留最近若干行
 └─ Diag（分析器）：只读账本做汇总与速率
```

【Agent 建议·未确认】三档在新模型下归位：

| 之前的说法 | 归到哪 | 说明 |
|---|---|---|
| 闹钟（睡眠） | 规划器的排期表 | 不是状态记录，是决策结果 |
| 体检报告 | 账本最后一行 | 「现在怎么样」= 最新一行 + 新鲜度判断 |
| 累积统计 | 对账本聚合 | 由账本行算出，或单独维护滚动计数（二选一，不许两份） |

【Agent 建议·未确认】账本必须有界：每条规则只保留最近 N 行（例如 8 行），环形覆盖；否则内存随机器数与运行时长线性增长。

【Agent 建议·未确认】界面呈现按来源区分：睡眠显示「休息中（按排期 12 tick 后再试）」；上一轮结果显示「拒收（0.3 秒前）」，超窗口显示「待测」；统计显示「本秒 3 个 / 累计 1.2 万」。

## 执行层三角色（已确认方向）

【用户已确认】2026-11-11：**规划器是最重要的逻辑分割**。执行层拆成三个角色：**规划器 / 执行器 / 分析器（原 Diag）**。

【用户已确认】2026-11-11：规划器负责把「机器的面记忆、轮询输入、阻挡模式、睡眠」等策略集中起来。

【Agent 建议·未确认】三角色 + 两份共享数据：

```
执行层
 ├─ 规划器（有跨轮记忆）
 │    读：账本（当前 + 历史）、配置、机器状态
 │    写：策略表
 │    禁止：碰方块、调机器接口、搬东西
 ├─ 执行器（无跨轮记忆）
 │    读：策略表、规则、机器状态
 │    写：账本一行 + 回报结果
 ├─ 分析器（原 Diag，只读）
 │    读：账本 + 策略表
 │    写：无（对外提供统计与展示数据）
 └─ 共享数据
      · 账本：Current（当前事实）+ History（过往事实，有界）
      · 策略表：排期、面记忆、轮询游标、退避状态、阻挡策略
```

【Agent 建议·未确认】规划器持有的策略表内容：

| 内容 | 解决什么 | 现在散在哪 |
|---|---|---|
| 排期：unit → 下次 tick + 原因 | 什么时候再跑 | NodeIoRunner.sleepIfIdle |
| 面记忆：规则 → 上次管用的面 | 不用每次六面模拟 | RunnerState.RouteTable |
| 轮询游标：规则起点、派单机器 | 避免前面的规则饿死后面的 | MachineIoRunner 按 now 取模 / NodeRuntime 游标 |
| 退避状态：空转时长、连续被拒次数 | 睡多久、被拒要不要降频 | RunnerState + ProviderReturnSweep.idleStep |
| 阻挡策略：上次是否因阻挡退出 | 派单节奏 | NodeCraftService 现场判断 |

【Agent 建议·未确认】关键收益：**执行器不再持有任何跨轮记忆**，它只做「给我一条规则和一份策略，我搬一次」。这样执行器可以单独验证、可以重放，行为不再依赖历史状态。

【Agent 建议·未确认】防止规划器膨胀成上帝类的约束：规划器只读「账本 + 配置 + 机器状态」，只写「策略表」。它不查方块、不调第三方机器接口、不搬运；需要机器内部信息（例如「机器里还有没有原料」）的判断留在执行器，结果经账本回到规划器。

【Agent 建议·未确认】执行单元分两类：

- **周期单元**（进排期表）：输入规则、输出规则、余量冲刷、产物回收。
- **事件单元**（不进排期表，同步调用）：CPU 派单 `pushPattern`。它有返回值和时序要求，不能等到下一个 tick。

【Agent 建议·未确认】到期队列与观测层共用同一个组件（「到什么时间做什么」），不各写一套：观测层是「到点去探」，执行层是「到点去搬」。

【Agent 建议·未确认】当前/过往的实现等价写法（语义不变、少一次搬移）：环形数组 + 头指针，写时 head 前移一格再覆盖；Current = Ring[head]，History = 其余格。若坚持物理分字段，则保留「先 push 再覆盖」的两步写。

【Agent 建议·未确认】主动侧在新结构里的位置：

| 场景 | 类型 | 归属 |
|---|---|---|
| 样板变更 → 解码放大 → 广告给 CPU | 事件（配置变更触发） | 执行层一次性动作 |
| CPU 派单 pushPattern | 事件（同步） | 执行器一次性入口，返回 boolean |
| 送余量 | 周期单元（节点级） | 排期表 |
| 收产物 | 周期单元（节点级） | 排期表 |

【Agent 建议·未确认】被动侧在新结构里：每条输入/输出规则是一个周期单元；执行 = 读规则 → 算量 → 调「机器侧写入口」。

【Agent 建议·未确认】账本不写档：重启后清空，规划器从头开始（第一轮全部跑一次），可接受。

## 主动侧：同步接单与 tick 执行的切分（讨论中）

【用户想法·待确认】2026-11-11：AE2 只跟节点层对话（`ICraftingProvider` 挂在哪，回调就在哪）。节点层当场回答「能接」之后，把材料清单交给执行层，由执行层执行；**执行仍然走 tick 逻辑**。

【Agent 建议·未确认】关键约束：`pushPattern` 调用期间，材料已经被 CPU 从 ME 网络抽出、此刻就在手上（`KeyCounter`）。返回 `true` 等于承诺「我收下了」，所以**必须当场给这批材料一个存放处**，不能「先回 true，等下一个 tick 再从头处理」。

【Agent 建议·未确认】两种切法：

- **切法 A（同步写为主）**：同步校验 → 直接往机器写 → 塞不下的进余量队列。现状即如此；代价是「已经写过就不能报失败」的 committed 语义要一直带着。
- **切法 B（只入队，tick 统一写）**：同步校验 → 把整单材料放进「待写入队列」→ 返回 true；tick 时执行层统一取队、选面、写入，写不掉的留在队里退避重试。

【Agent 建议·未确认】倾向切法 B 的理由：

1. 同步路径完全不碰机器，极短、永不半途失败，committed 语义消失。
2. 「派单材料」与「余量（塞不下的零头）」合并成**同一个待写入队列**，不再维护两套。
3. `isBusy` 天然等于「待写入队列非空」，语义单一。
4. 符合用户模型：节点层只做「接单 + 交清单」，执行层按 tick 执行。

【Agent 建议·未确认】切法 B 的代价与要求：队列有上限（一单材料量可能大）；服务端停止 / 节点拆除时必须兜底（退回网络，退不回则掉落，不许静默丢）；交付延迟 +1 tick（约 50ms）。

## 回收判据与模式（讨论中）

【用户已确认】2026-11-11：账本 = **变化序列**；账本是**分析器产出的结论之一**，属于短期结论。8 行/单元的内存开销可接受（1000 台 × 16 规则 ≈ 几 MB）。

【用户想法·待确认】2026-11-11：机器通常自带两道约束——① 不让抽走进料、只让抽产物；② 输入面只能进、输出面只能出。因此回收可以「无视白名单直接抽」，把「抽错」当成玩家配置责任（与管道一致），并允许玩家配置抽哪个面 / 哪些槽位。

【Agent 建议·未确认】「直接抽」必须堵一个坑：我们自己送进去的原料若被回收抽回来，会形成「送进去 → 被抽回 → 再送」的死循环，机器永远做不了事。所以「直接抽」的安全前提是「机器自己限制 extract 的内容」或「回收限定在输出面」。

【Agent 建议·未确认】链式样板（样板 B 产出 X、样板 A 又用 X 作输入）下，「排除输入并集」会永远收不走 X，链断掉。判据必须产物优先：

| 优先级 | 判据 | 动作 |
|---|---|---|
| 1 | 是产物（主动节点：样板产物并集） | 收 |
| 2 | 在玩家显式「回收清单」里 | 收 |
| 3 | 是排除集（我们主动送进去的东西） | 不收 |
| 4 | 都不是 | 由回收模式决定 |

【Agent 建议·未确认】排除集来源：主动节点用样板输入并集（已有）；纯被动节点用输入规则的 key 并集。

【Agent 建议·未确认】回收模式三档（配置开关）：

| 模式 | 行为 | 适用 |
|---|---|---|
| DIRECT 直接抽 | 不看 key，扫（可限定的）面就抽 | 信任机器分区 / 玩家自担 |
| AUTO 自动 | 只在「抽得出来、塞不进去」的面抽（启发式判为输出面） | 默认推荐 |
| SAFE 判据 | 按上面四个优先级过滤 | 机器不分区时的安全网 |

【Agent 建议·未确认】面配置：允许玩家限定回收面（与管道一致）；默认 AUTO 自动判定输出面，玩家可覆盖。

【Agent 建议·未确认】为什么其他管道「随便抽」不怕：① 玩家把它放在正确的面上；② 很多机器按面暴露不同槽位；③ 抽错算玩家配置责任。我们的差异是「自动扫六面」，所以要么信机器（DIRECT）、要么信启发式（AUTO）、要么自己判（SAFE）。

| `lastAttemptAt` | tick | 上次尝试的时间 | 每执行一行 |
| `lastSuccessAt` | tick | 上次成功的时间 | 成功时 |
| `lastFailureAt` | tick | 上次失败的时间 | 失败时 |
| `idleTicks` | 时长 | 连续空转时长 | 失败 +1 / 成功清零 |
| `rejectStreak` | 次数 | 连续被拒次数 | REJECTED +1 / 其它清零 |
| `reasonCounts` | 计数 | 各原因累计次数 | 每行 +1 |
| `faceHint` | 面 | 上次成功的面 | 成功记录 / 失败清除 |

【Agent 建议·未确认】节点级（主动侧）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `pendingCount` | 计数 | 队列条目数（= isBusy） |
| `pendingOldestAt` | tick | 最老条目的入队时间 |
| `entryAttempts` | 次数 | 当前条目已尝试次数 |
| `entryLastError` | 枚举 | 当前条目上次失败原因 |
| `deliveredTotal` | 计数 | 累计投递数量 |

【Agent 建议·未确认】重置规则：全部由「结果 + 表单」驱动，不引入新信号——单元离开表单即丢弃；重新进入表单从零开始；单元 key 变化即身份变化（旧的丢、新的建）；面记忆在写入失败时就地清除。

【Agent 建议·未确认】**聚合不靠账本行历史**：账本写一行时顺带 O(1) 更新计数器，历史被压缩进计数器，不需要回放。账本 8 行是「明细（会滚掉）」，计数器是「摘要（不滚）」，滚掉的旧行信息已累加进 `reasonCounts` 等。

【Agent 建议·未确认】三类聚合的维护方式：

| 类型 | 例子 | 维护方式 |
|---|---|---|
| 连续量 | idleTicks、rejectStreak | 增量：成功/非拒收即清零 |
| 累计量 | reasonCounts、deliveredTotal | 增量：每行 +1 / +n |
| 滑窗量（最近 N tick 成功率） | —— | 需要滚动桶或指数衰减；暂不做 |

## 其他未明确项（讨论中）

### 观测层的形状（Agent 建议）

【Agent 建议·未确认】每 tick **一趟遍历**同时做两件事，不必再造「登记表」：

```
遍历配置里的全部单元（有上限，O(单元数)）
  ├─ 读这条单元的事实缓存（不探世界）
  ├─ 事实到期（nextProbeAt 到点）→ 放进本 tick 的探测队列（全服最多 64 次）
  └─ 事实可用 → 放进 IO 表单
```

【Agent 建议·未确认】「配置」本身就是登记表：不需要额外维护一张「谁被引用」的表，配置里的单元就是全部引用。探测预算只限制「真正探几次」，不改变遍历成本。

【Agent 建议·未确认】节点卡片的数据由三份真相读时拼：

| 规则数、机器数 | 配置 |
| 正在搬 / 等料 / 堵塞 / 空闲 | 执行结论聚合（各单元 `reasonCounts` / 账本尾行） |

【Agent 建议·未确认】卡片上的「+」按钮：新增规则（普通规则 or 通配自动输出规则）。规则增删走配置事件（配置层），不由执行层直接改。

### 主动单要不要「任务身份」

【Agent 建议·未确认】不做任务台账，只做可观测。理由：

- AE2 的 CPU 自己管任务生命周期，会取消、重试、改派；我们再建一份台账必然与它打架。
- 我们只承诺两件事：材料进机器、产物回网络。

【Agent 建议·未确认】替代做法 —— 暴露健康指标：

- `pendingOldestAt`：有单卡了多久（超过阈值界面标黄/红）。
- `entryAttempts` + `entryLastError`：为什么卡（满 / 没面 / 机器不在）。
- 玩家据此自己开阻挡模式或去掏机器。

## 观测层重构（待确认）
